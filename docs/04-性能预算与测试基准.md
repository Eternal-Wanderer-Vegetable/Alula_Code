# 04 · 性能预算与测试基准

## 1. 测量口径（先统一语言，再谈数字）

### 1.1 必须统计整个进程树并按平台选对指标

| 平台 | 主指标 | 采集方式 |
|---|---|---|
| Windows | **Private Bytes（私有提交）** 进程树求和 | `GetProcessMemoryInfo`/`tasklist`；`tools/mem-probe` 统一封装 |
| Linux | **PSS（比例集大小）** 进程树求和 | `smaps_rollup` 逐进程读取（PID 树：主进程+子进程） |
| macOS | 物理内存占用（phys_footprint） | `footprint`/`task_info` |

**禁止直接累加各进程 RSS**——共享页（WebView 时代的教训、动态库、GPU 缓冲）会被
重复计入。所有报告必须给出「进程 × 指标」明细表 + 求和口径说明。

### 1.2 归因分解（每份报告必填）

```
总占用 = 编辑器主进程(Flutter UI)
       + Rust Core（同进程或 sidecar，注明）
       + 语言服务器（按服务器逐个列出）
       + 扩展宿主（若启用）
       + 终端/其他工具进程
```

语言服务器内存常常远超编辑器本体（rust-analyzer 大工作区、clangd 索引缓存），
必须单列，防止「编辑器很省」被服务器开销掩盖，也防止反过来甩锅。

### 1.3 两层指标

- **基线内存**：空工作台/普通项目，无 LSP 无扩展宿主；
- **完整环境内存**：基线 + 实际启动的服务。两层数据永远成对出现。

## 2. 设计预算表（验收线见文档 03 的 DoD）

| 场景 | 预算 | 性质 |
|---|---|---|
| 空白窗口、无语言服务 | ≤ 200 MiB | 挑战值（300 为可接受下限） |
| 普通项目、未启动 LSP | ≤ 250 MiB | 目标值 |
| Rust/Python 项目 + LSP | Rust + rust-analyzer ≤ 500 MiB 目标暂停；保留服务分项与进程树基线 | P14 整体架构复刻后重新定标 |
| 同功能对比 VS Code | −50% | **主竞争验收线** |
| 冷启动至可交互 | ≤ 2 s | 目标值 |
| 空闲 CPU | ≈ 0% | 硬性（无轮询、无空转动画） |

预算不是承诺值：所有「未达标」项在报告中需给出差距归因（如 Flutter 引擎常驻 X、
Impeller 纹理 Y、语言服务器 Z）。**不为凑 200 MiB 牺牲编辑稳定性。**

### 2.1 执行顺序

P00–P13 先完成 VS Code 整体架构与默认功能复刻。此阶段记录可比较的进程树基线，并保持可编辑、可保存、无卡死/数据丢失及服务可回收；不为达到数值占用目标提前删减或调优功能。Rust + rust-analyzer 的 500 MiB 目标暂时退出验收门，已有数据继续作为基线。全功能占用优化集中在 P14，最终数值目标在届时结合完整功能与同场景 VS Code 对照重新确定。

## 3. 基准测试套件（tools/bench）

### 3.1 场景矩阵

| 维度 | 取值 |
|---|---|
| 平台 | Windows 11 / Ubuntu(X11+Wayland 各一) / macOS |
| 项目 | fixtures：小 Python、中 Rust（含 workspace）、大 C++（CMake+compile_commands）、超大单文件(≥5 万行) |
| 语言服务 | 无 / 单服务器启用 / 全启用 |
| 扩展宿主 | 无 / 启用+1 个目标 VSIX |
| 负载 | 空载、编辑 30 分钟（脚本化按键流）、模型并行（可选复现场景：占用 60% RAM 的哑负载进程） |

### 3.2 每场景采集的时间点

启动峰值 → 稳定态（启动后 1 min）→ 空闲 10 min → 编辑 30 min 后 → 关闭项目后
（验证回收，等待 30s 再采样）。

### 3.3 内存压力/OOM 扫描（借鉴 LVCE Memory Benchmark 方法学）

- 限额扫描：64/128/256/512/1024 MiB 档位（Linux cgroup v2 memory.max；Windows Job
  Object memory limit）；
- 关闭 swap（Linux），记录 OOM 事件；
- 每档位重复 ≥3 次，通过标准：**能启动、能编辑、能保存**，且低资源模式在限额内
  正确降级而非卡死；
- 输出「最低可工作预算」——这比平均内存更贴近用户（跑模型）的真实痛处。

### 3.4 报告

每次运行产出 Markdown + JSON（进版本库或 CI artifact）：明细表、时间线图、
与上一版/VS Code 基线的对比、预算达成状态。发布决策依据此报告。

## 4. 测试矩阵

| 类型 | 内容 | 通过要求 |
|---|---|---|
| 编辑可靠性 | 保存/撤销/重做/编码(UTF-8/GBK)/换行符(LF/CRLF)/大文件 | 内容零丢失（哈希校验） |
| 语言服务 | fixtures 上补全/诊断/跳转/格式化/重命名 | 与预期快照一致；位置精确（UTF-16 换算用例必含） |
| VSIX 兼容 | 安装→激活→功能→卸载→资源回收 | 无未处理异常；功能真实来自扩展 |
| 性能回归 | 基准套件全场景 | 不超预算 + 不劣化上一版 5% 以上 |
| 故障注入 | 强杀 LSP/扩展宿主/终端；限额触发；模拟磁盘满 | 可恢复、文件不丢、UI 不冻结 |
| 跨平台 GUI | 三平台：输入、渲染、快捷键 | 全绿 |

### 专项（高风险，单列）

- **IME**：中文（微软拼音/搜狗 + Linux fcitx5/ibus）组合中撤销、光标跳转、
  候选窗定位；三平台分别过；
- **字体与宽度**：中英文混排等宽性、连字（ligature）开关、Emoji 宽度；
- **HiDPI/多显示器**：缩放 100/125/150/200% 下光标与选区对齐；
- **Wayland/X11** 分别跑 GUI 冒烟（Flutter Linux 已知存在与 GPU 驱动相关的
  渲染问题报告，需实测覆盖）。

## 5. 自动化与 CI

| 层 | 工具 | 触发 |
|---|---|---|
| Rust 单元测试 | `cargo test`（全 crate，含换算/监督树/journal） | 每次提交 |
| Flutter 组件/集成测试 | `flutter test` / `integration_test` | 每次提交 |
| 端到端 GUI | Flutter integration_test 驱动真应用（桌面） | 每日/发版 |
| 兼容性套件 | `tests/compatibility` 脚本（VSIX 生命周期） | 每日（Phase 2 起） |
| 基准套件 | `tools/bench` 全矩阵 | 每周 + 发版前（三平台 runner） |
| 压力/OOM 扫描 | `tests/stress` | 发版前必跑 |

CI 平台：GitHub Actions（windows/linux/macos 三矩阵）。基准跑在固定规格的
runner 上并在报告中注明环境；跨版本对比仅在同 runner 内进行。

## 6. 一次性基线采集（Phase 0 立即执行）

1. 用 `tools/mem-probe` 采集用户当前 VS Code（含其扩展与语言服务器）真实
   工作场景基线 —— 这是 −50% 目标的分母；
2. 同法采集 Zed、Lapce、VSCodium 作参照系；
3. 归档至 `docs/baselines/`，注明日期与机器配置。
