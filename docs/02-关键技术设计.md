# 02 · 仓库结构与关键技术设计

## 1. 仓库结构

项目名 **Alula Code**，仓库根目录（`E:\Alula_Code`）即项目根。
`docs/` 已存在（本方案文档），其余顶层目录随开发逐步创建：

```text
Alula_Code/                     # 项目根（= 仓库根）
├── app/                          # Flutter 桌面应用（唯一 GUI 入口）
│   ├── lib/
│   │   ├── workbench/            # 窗口布局、面板、状态栏、命令面板
│   │   ├── editor_ui/            # 编辑视图（封装候选编辑组件，隔离依赖）
│   │   ├── workspace_ui/         # 文件树、标签页、搜索界面
│   │   ├── git_ui/               # Git 面板（diff/blame/stage 视图）
│   │   ├── terminal_ui/          # 终端视图（PTY 桥接显示层）
│   │   └── bridge/               # flutter_rust_bridge 生成代码与 Dart 侧适配
│   └── test/                     # widget test / integration_test/
│
├── crates/                       # Cargo workspace（Rust Core，全部可独立测试）
│   ├── editor-buffer/            # Rope(Ropey)、增量事务、位置换算
│   ├── editor-lang/              # Tree-sitter 集成、语法/折叠/符号
│   ├── editor-lsp/               # LSP 客户端、服务器注册与生命周期
│   ├── editor-workspace/         # 文件监视、ripgrep 搜索、Git 服务
│   ├── editor-process/           # 子进程监督树、限额、重启
│   ├── editor-rcm/               # 低资源模式（压力信号、降级阶梯）
│   ├── editor-doc/               # 原子保存、恢复日志、检查点
│   └── editor-core/              # 组装层：对 FFI 暴露统一 API（facade）
│
├── sidecars/
│   └── node-extension-host/      # 可选 Node.js 扩展宿主（Phase 2，接口先行）
│       ├── src/                  # 宿主进程：VSIX 加载、激活事件循环
│       └── protocol/             # 与 Rust Core 的 IPC 协议定义（JSON Schema）
│
├── tools/
│   ├── mem-probe/                # 进程树内存采集（Win Private Bytes / Linux PSS）
│   └── bench/                    # 基准测试编排（场景、负载、报告生成）
│
├── tests/
│   ├── fixtures/                 # 标准测试工程（python/cpp/rust 各一，含典型缺陷）
│   ├── compatibility/            # VSIX 兼容性测试（安装→激活→调用→卸载→回收）
│   └── stress/                   # 内存压力/OOM/故障注入脚本
│
├── docs/                         # 本方案文档 + 原始讨论存档（appendix-原始讨论全文.txt）
└── Cargo.toml                    # workspace 根
```

要点：

- `editor-core` 是唯一对 FFI 暴露 API 的 crate，其余 crate 不感知 Flutter。
- `app/lib/editor_ui/` 必须把第三方编辑组件隔离在一层包装内（候选：CodeForge、
  Re-Editor、flutter_code_editor），保证组件可替换——这是 Phase 0 评测的前置条件。
- `sidecars/node-extension-host` 在 Phase 0~1 只放协议定义与实验代码，
  **不假设其可用**。

## 2. FFI 同步协议（Flutter ↔ Rust）

### 2.1 设计原则

1. Flutter 侧编辑器即时响应键盘（输入延迟不受 FFI 影响）；
2. **绝不逐字符传全文**：内容以增量操作（insert/delete/range replace）+ 单调递增版本号同步；
3. Rust 侧持有同步副本用于分析（Tree-sitter/LSP），异步结果必须携带其计算时的版本号；
4. Flutter 收到结果时做版本检查，**过期结果直接丢弃**，防止覆盖较新编辑。

### 2.2 接口草签（以 flutter_rust_bridge 生成绑定为最终形态）

```rust
// editor-core 对 FFI 暴露的核心面（示意）

/// 打开文档，返回初始全文 + 初始版本。此后全量传输仅此一次。
fn doc_open(uri: String, content: String) -> DocState;

/// 增量编辑。ops 按序应用；version 必须等于当前版本+1，否则返回
/// SyncMismatch 由 Dart 侧重新对齐（重新拉全文）。
fn doc_apply(uri: String, version: u64, ops: Vec<TextOp>) -> Result<DocState, SyncError>;

enum TextOp {
    Insert { offset_utf16: usize, text: String },
    Delete { offset_utf16: usize, len_utf16: usize },
}

/// 可视范围通知（虚拟化渲染：Rust 只返回可见行±预读行的排版数据）
fn viewport_update(uri: String, first_line: usize, last_line: usize);

/// 事件流（Rust → Dart，stream 形式）
enum CoreEvent {
    Diagnostics { uri: String, version: u64, items: Vec<DiagItem> },
    SyntaxUpdated { uri: String, version: u64 },
    Completion { id: RequestId, version: u64, items: Vec<CompItem> },
    ServerState { server: ServerId, state: ServerState }, // Starting/Ready/Crashed/Restarting
    PressureLevel { level: PressureLevel },                // Normal/Warn/Critical
}
```

### 2.3 位置换算（必须在 V1 就做对）

三个世界：LSP 用 **UTF-16 code unit**；Rust 字符串是 **UTF-8 byte**；
Dart `String` 也是 UTF-16。中文、Emoji、组合字符会让三者互不相同。

- 统一内部坐标：Rust 侧 `editor-buffer` 提供
  `utf16_offset <-> utf8_offset <-> line/column` 的双向换算（基于 Ropey 行索引 + 缓存）；
- 所有跨 FFI 边界的 offset 一律使用 **UTF-16 口径**（与 Dart/LSP 天然一致），
  Rust 内部分析前再转 UTF-8；
- 该换算层必须有独立单元测试集（覆盖：中文、Emoji（含 surrogate pair）、
  组合字符、CRLF、文件末尾无换行、BOM）。
- 诊断波浪线/补全位置错乱是这类换算错误的典型症状，列入 Phase 1 验收项。

### 2.4 版本对齐与冲突恢复

- 正常流：Dart 维护待发送 op 队列，Rust 确认版本后异步回包；
- 异常流（版本失配、进程重启）：Dart 调 `doc_resync(uri)` 拉取权威全文重建状态；
  丢弃所有在途异步结果直到 resync 完成。

### 2.5 Rust 权威文档有界范围读取与行定位（ABI v12–v14）

ABI v12 起，P03 编辑器视口通过 `alula_doc_read_range(id, start_utf16, max_len_utf16)` 从 Rust
Rope 读取短快照，不以 `doc_resync` 传输视口内容。单次请求最多 64 Ki UTF-16 单元；
返回同一快照的文档版本、全文 UTF-16 长度、行数、范围绝对起点/终点、起点行列与文本。
起点落在代理对内部时拒绝；终点若切开代理对则向前收缩一个单元；仅请求 1 单元且
当前位置是补充平面字符时返回完整 2 单元字符，以保证分页前进且不拆 Unicode 标量。
BOM 与 CRLF 按原文本返回。Dart 包装 `AlulaDoc.readRange` 将快照版本同步到文档句柄。

ABI v13 增加 `alula_doc_line_offset(id, line)`，通过 Rope 行索引直接返回指定 0-based
行起点的绝对 UTF-16 offset、同一版本、全文长度与行数。该路径不遍历或复制行前全文；
越界行明确返回 `InvalidLine`，Dart 包装为 `AlulaDoc.lineOffset`。

ABI v14 增加 `alula_doc_read_lines`，一次返回 Rust Rope 中一页按行 UTF-16 水平窗口，
并附带同一版本、全文长度和行数。请求最多 256 行，单行与整页 UTF-16 上限分别由
调用者声明且总预算不得超过 64 Ki；实现裁掉 CRLF/LF 分隔符，水平起点若落在代理对中间
则回退到该标量起点。Dart `AlulaDoc.readLines` 只接收页面，不读取 `doc_resync` 全文。

P03.3 已选定“Rust 唯一文档文本 + Flutter 有界分页绘制/选择”的后续控件路径；原型页
每次取 32 行，每行最多 2,048 UTF-16 单元，单页最多 64 Ki，单个视图最多保留 3 页缓存，
各视图分别持有滚动与选择状态。CodeForge 直接绑定需要在 Dart 再持有完整 Rope，现有
TextField 仍持有完整 `TextEditingController`，两者均不作为最终文档文本所有者。P03.3
原型仍为只读，不代表工作台已切换；Delta 输入窗口、真实键盘写回、IME、键盘/屏幕阅读器
无障碍及三平台验收分别留在 P03.4–P03.7。原型也尚未给出帧时延或整机内存结论。

## 3. LSP 管理器

### 3.1 注册表与启动策略

```rust
struct ServerRegistry {
    /// (workspace_root, language_id) -> 一个服务器进程
    active: HashMap<(WorkspaceId, LanguageId), SupervisedServer>,
}
```

- **一区一语言一服务器**：同一工作区同语言复用进程，绝不每文件一个；
- 启动时机（按需）：首次触发补全 / 打开该语言文件后首次保存 / 用户显式请求诊断；
  仅打开文件浏览不启动；
- 关闭时机：工作区关闭、语言文件全部关闭超过空闲阈值（可配置）、低资源模式降级；
- 服务器发现：优先用户配置（绝对路径/命令行）→ 内置注册表（见下）→ PATH 探测。

### 3.2 内置注册表（V1 目标）

| 语言 | 服务器 | 说明 |
|---|---|---|
| Python | basedpyright（或 pyright）+ Ruff | 类型检查/补全 + 格式化/lint；两者可并存，Ruff 以 `ruff server` 形式 |
| C/C++ | clangd | 需处理 `compile_commands.json` 发现（CMake 项目重点测试） |
| Rust | rust-analyzer | Cargo 项目识别；大工作区索引内存单独归因汇报 |

### 3.3 防重复服务（扩展接管协议）

启用原版 rust-analyzer VSIX 后，**必须停用编辑器原生启动的同类服务器**，
由扩展侧服务器接管——否则双索引双诊断。实现为 `ServerRegistry` 的所有权声明：
某语言的服务权被扩展宿主持有时，原生通道静默让位，UI 显示当前服务来源。

### 3.4 参考

客户端协议层参考 Helix 的 `helix-lsp` 组织方式（请求/通知路由、多服务器复用），
按需重写而非直接依赖（MPL-2.0，见文档 05§3）。

## 4. 进程监督树（editor-process）

所有子进程（LSP、PTY、Git 调用、扩展宿主）由统一监督器管理：

- **启动**：统一入口 spawn，记录元数据（类型、归属工作区、启动原因、资源限额）；
- **监督**：崩溃检测（退出码/信号）、内存超限检测（周期采样，超预算先告警）；
- **重启策略**：LSP 指数退避重启（上限 N 次，超过则标记 Failed 并提示手动重启）；
  扩展宿主崩溃重启需重新走激活流程且不自动重试超过 1 次；
- **回收**：工作区关闭 → 按依赖序终止全部子进程 → 等待 → 强杀兜底；
  「关闭工作区后进程树为空」是 Phase 1 验收项；
- **隔离不变量**：任何子进程都不持有编辑缓冲区唯一副本；所有保存路径只经 Rust Core。

## 5. 文本缓冲区归属（分两步走）

| | V1（Phase 1） | V2（Phase 3+ 评估） |
|---|---|---|
| 权威编辑状态 | Flutter 编辑组件内 | Rust（Ropey） |
| Rust 侧 | 同步分析副本（增量同步，见 §2） | 唯一权威 |
| Flutter 侧 | 组件自渲染 | 仅缓存可视区文本+排版结果 |
| 内存代价 | 大文件双份持有 | 单份 |
| 风险 | 低 | IME/多光标/撤销/滚动同步复杂度高，须原型验证后决定 |

**不要在原型验证前认定 V2 必然更优**——这是讨论中明确的告诫。

## 6. 低资源模式（Resource-Constrained Mode, editor-rcm）

### 6.1 触发信号（真实压力信号，非固定百分比）

- Windows：`GlobalMemoryStatusEx`（可用物理内存）+ **提交内存百分比
  （commit charge / commit limit）为主信号**——2026-10-26 实测本机故障模式是
  commit 耗尽（模型进程提交 86–93 GB 击穿 107 GB 上限，物理内存尚有余量），
  见 docs/07-诊断-VSCode卡死归因.md；
- Linux：`/proc/meminfo`（MemAvailable）+ PSI（`/proc/pressure/memory`）；
- macOS：`host_statistics64` 物理内存压力等级；
- 辅助输入：用户手动开关、子进程超限额事件。

### 6.2 降级阶梯（PressureLevel：Normal → Warn → Critical）

| 级别 | 保留 | 暂停/降级 |
|---|---|---|
| Normal | 全部功能 | — |
| Warn | 编辑、保存、诊断 | 暂停后台索引与预取；降低 Tree-sitter 并行度；冻结非活跃工作区的 LSP（不发 didChange，仅排队） |
| Critical | **输入、滚动、撤销、保存、崩溃恢复** | 停止全部 LSP 请求（保进程可恢复）；禁用动画/语法高亮降级为纯文本；提示用户 |

恢复迟滞：压力回落后延迟 T 秒且逐级恢复，避免抖动。

### 6.3 兜底（GUI 自身被阻塞/终止时）

- **原子保存**：写临时文件 + `fsync` + `rename`，任何时刻断电/被杀不产生半文件；
- **恢复日志（journal）**：每次编辑以 append-only 记录（uri, version, ops），
  检查点间隔可配（默认每 200 次操作或 30s 全量快照）；
- 启动时发现未正常关闭的 journal → 提示恢复未保存内容；
- journal 属于 Rust Core 职责，不依赖 Flutter 存活。

## 7. 扩展兼容层（Phase 2 主体，接口先行）

### 7.1 扩展分级

| 级 | 类型 | 难度 | 计划 |
|---|---|---|---|
| A | 声明式：主题、语法(TextMate)、代码片段——无运行时入口 | 低 | Phase 1 即支持数据文件 |
| B | `browser` 入口的 Web 扩展 | 中 | Phase 2 中段评估（无 WebView 工作台下需要 JS 沙箱，成本高） |
| C | `main` 入口的 Node.js 桌面扩展 | 高 | Phase 2 核心：独立 Node 宿主进程 |

### 7.2 进程与通信模型

```
Flutter UI ↔ Rust Core ↔ [受控 IPC: JSON-RPC over stdio] ↔ node-extension-host
```

- 宿主是**独立 Node.js 进程**（随应用分发运行时或首启下载，用户可禁用）；
- API Bridge 在宿主内实现 `vscode.*` 表面，把调用映射到 Rust/Flutter 能力；
- 首批映射范围（够用即止）：`workspace`（文件读写、配置、变更事件）、
  `languages`（诊断/补全/代码操作提供者注册）、`window`（消息、状态栏、输出通道）、
  `commands`（注册与执行）；
- 明确警告：**有独立 Node 进程 ≠ 自动兼容**。扩展依赖大量工作台状态、编辑器对象
  与事件语义；首批只承诺 4 个目标 VSIX 的行为级可用。

### 7.3 VSIX 生命周期管理

安装（Open VSX 下载/本地导入）→ 校验（版本、依赖、引擎声明）→ 登记 →
激活事件监听（`onLanguage` / `onCommand` / `workspaceContains` 等最小集）→
按需激活 → 卸载（含子进程与缓存清理）。
全过程产生可观测日志，「安装成功 ≠ 兼容成功」——验收一律看功能行为（文档 04§4）。

### 7.4 Webview 类扩展（Markdown 预览等）

仅允许**局部可选 WebView**承载该类面板（VS Code 自身也是这样做的），
工作台主体仍不依赖 WebView。列入 Phase 3 之后的 backlog，非目标内必做项。

## 8. 终端与搜索

- 终端：`xterm.dart`（或等价）渲染 + Rust 侧 PTY（`portable-pty`）；
  **用户打开终端面板才 spawn shell**，关闭面板即回收进程；
- 搜索：Rust 侧嵌入 `grep-searcher`/ripgrep 核心做全项目正则搜索，
  结果流式回传；不做常驻索引服务。
