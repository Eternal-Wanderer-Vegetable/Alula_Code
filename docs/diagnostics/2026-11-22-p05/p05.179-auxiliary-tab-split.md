# P05.179 / feat-231 · 辅助窗标签回拖边缘建组

依赖 P05.45 的编辑器组拆分和 P05.178 的跨窗移交。活动文本标签拖到主窗编辑区的边缘时，预览对应半区。放下后在目标旁创建编辑器组。中心区沿用 P05.178 的追加流程，标签落点沿用标签顺序。主窗完成文本、选区和同路径冲突检查后才创建新组。拒收保留原布局与源窗。

## 固定版本核对

在 Code-OSS 1.145.0、`4bda7217fc83e8e838b1edd9ebaf21bb9b498c7e` 的固定源码中，拖动单个编辑器使用 10% 边缘带，默认水平排布下按横向三分和纵向半分判定方向。拖动期间 Windows、Linux 使用 Alt，macOS 使用 Shift 反转拆分。源组只有一个编辑器且启用关闭空组时，固定版将该组移入并聚焦目标。单文档辅助窗复用已有主窗布局模型，以同方向建组并交还脏文档。[边缘、方向和预览](https://github.com/microsoft/vscode/blob/4bda7217fc83e8e838b1edd9ebaf21bb9b498c7e/src/vs/workbench/browser/parts/editor/editorDropTarget.ts#L382-L503) · [单编辑器源组移交](https://github.com/microsoft/vscode/blob/4bda7217fc83e8e838b1edd9ebaf21bb9b498c7e/src/vs/workbench/browser/parts/editor/editorDropTarget.ts#L307-L342)

Linux 初轮发现键盘事件留在正在拖动的辅助窗或系统拖放会话中。主窗在有效的原生辅助窗正文拖放回调中读取修饰键，因此可在指针到达边缘后按下 Alt 切换为中心预览。Linux 使用 GTK 指针的当前修饰状态，Windows 查询 VK_MENU 的按下位，macOS 查询 AppKit 当前 Shift 状态。[GTK](https://docs.gtk.org/gdk3/method.Device.get_state.html) · [Win32](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-getasynckeystate) · [AppKit](https://developer.apple.com/documentation/appkit/nsevent/modifierflags-swift.type.property?changes=_2_8)

Alt 生效后，Linux 仍出现落点正确但编辑器失焦。X11 和 Flutter 轨迹显示主窗获得原生焦点时收到合成 Alt 按下，实际松开时旧标题栏逻辑按单独按 Alt 处理。现仅从实际 Alt 按下开始判定标题栏快捷键。复验确认 Alt 释放后目标编辑器保有焦点，单独按 Alt 激活菜单及实际助记键测试仍通过。
