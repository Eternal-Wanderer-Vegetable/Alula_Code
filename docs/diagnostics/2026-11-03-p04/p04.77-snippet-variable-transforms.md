# P04.77 / EDT-12d1: Snippet Variable Transforms

## Scope and compatibility target

This slice implements TextMate variable transforms for the fixed Code-OSS 1.145.0 snippet grammar, `${VAR/regex/format/options}`. It resolves variable values first, applies a regular-expression replacement, and inserts the result as plain text. It does not reparse transformed output as snippet syntax. Placeholder transforms, which update a tabstop when leaving it, remain a separate open slice.

- [`snippetParser.ts` at `4bda7217`](https://github.com/microsoft/vscode/blob/4bda7217fc83e8e838b1edd9ebaf21bb9b498c7e/src/vs/editor/contrib/snippet/browser/snippetParser.ts)
- [`snippet.md` at `4bda7217`](https://github.com/microsoft/vscode/blob/4bda7217fc83e8e838b1edd9ebaf21bb9b498c7e/src/vs/editor/contrib/snippet/browser/snippet.md)

No Rust crate or FFI ABI changed. Successful expansions continue through the existing Rust-authoritative edit, undo, dirty, and save/readback path. Invalid expressions, unsupported flags/formats, size-limit violations, and timeouts fail before applying an edit.

## Implementation

- The parser now accepts variable transforms and evaluates each expansion's transforms in one disposable Dart isolate. Supported flags are `g`, `i`, `m`, `s`, and `u`; formats include numeric captures, `upcase`, `downcase`, `capitalize`, `camelcase`, `pascalcase`, `kebabcase`, `snakecase`, and TextMate's conditional/default forms.
- An unresolved variable is transformed as an empty string. Escaped delimiters are retained correctly, and transform-format expressions are skipped by the workbench's variable-detection scan so a format literal does not trigger an unrelated clipboard/current-line read.
- Limits are 64 transforms, 512 UTF-16 units each for regex and format, 256 Ki UTF-16 units of aggregate input, 256 Ki UTF-16 units of total replacement output, and 750 ms per worker request. Existing template/expanded-text limits remain in force. The isolate is killed on reply, error, or timeout.
- Variable expansion is now asynchronous. After it completes, the workbench rechecks the active document, Rust version, input-window range/text, selection, editing value, additional selections, and input-field instance. If the document changed or closed while the worker ran, the insertion is discarded rather than writing through a stale or disposed controller.
- The timeout/format error is converted to `SnippetTemplateException` before the workbench mutates the document. Placeholder transforms still fail closed.

## Resource probe

`tools/mem-probe` watched a standalone Dart VM harness on the WSL/Linux runner, with 100 sequential expansions of a 128 Ki UTF-16 value. The comparison used the same VM/import/wait interval; one variant expanded a plain variable, and the other applied a global capture replacement in the worker isolate. Each run sampled for 8 seconds at 100 ms intervals (79 samples):

| Harness mode | Peak Private | Stable Private | Final Private |
|---|---:|---:|---:|
| Plain variable | 211.8 MiB | 180.3 MiB | 180.3 MiB |
| Variable transform | 216.8 MiB | 175.8 MiB | 175.8 MiB |
| Difference | +5.0 MiB | −4.5 MiB | −4.5 MiB |

The short run observed no retained-memory increase after the worker requests, with a roughly 5 MiB higher sampled peak. This is a Dart harness measurement, not an Alula GUI baseline; it is not directly comparable to the Windows 11 workbench baseline in [`docs/baselines/2026-10-26/README.md`](../../baselines/2026-10-26/README.md). The isolate runs inside the same process, and short peaks may be undersampled. The resource caps are therefore the primary bound; this probe is supporting evidence only.

## CI-failure and crash relation

The first workbench integration attempt exposed a real async lifecycle hazard in this new path: the regex worker could complete after its editor controller was disposed. The post-await snapshot guard and two workbench regression cases now cover editing and closing during resolution. A fake-native channel context lets these widget tests wait for the isolate without starting local GUI services.

This is evidence for a new snippet-resolution race that could cause a test/UI exception if left unchecked. It does not identify the cause of the historical Windows `0xC000041D` or macOS SIGSEGV, and it does not show that those incidents were caused by CI. Existing recent CI red jobs remain a mixture of probe, accessibility, and injection-route failures; classify each recurrence by its failing step, process exit code, and crash artifact. P04.77 PR CI and Platform Availability results are recorded below.

The newly reproduced failure was a Flutter/Dart controller-lifecycle exception after the editor was closed while an isolate was resolving a transform; it was not an OS process crash. The two close/edit regression cases now verify that no stale edit or disposed-controller access occurs. The P04.77 hosted CI passed those tests; that rules out a failure in this hosted run, but it cannot connect the old native crash signatures to this snippet feature.
