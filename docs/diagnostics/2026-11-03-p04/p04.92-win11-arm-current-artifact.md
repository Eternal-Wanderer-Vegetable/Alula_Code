Historical run [`41454766973`](https://github.com/Eternal-Wanderer-Vegetable/Alula_Code/actions/runs/41454766973) replayed the x64 Release artifact from [`41109679662`](https://github.com/Eternal-Wanderer-Vegetable/Alula_Code/actions/runs/41109679662), source `d5319369`. That is a confirmed old-binary crash. At the time, its source-level cause was unknown; the follow-up comparison below narrows the likely cause.

The follow-up asked whether the current x64 Release build also crashed on Windows 11 ARM and whether the repeated validation failures represented app crashes.

## Interpretation

Source comparison found a direct teardown-order difference. In artifact source `d5319369`, `FlutterWindow` remained alive until `wWinMain` returned, so the explicit `CoUninitialize()` ran before the `FlutterWindow` destructor; `FlutterWindow::OnDestroy()` releases its `FlutterViewController`. Commit [`c2b787f`](https://github.com/Eternal-Wanderer-Vegetable/Alula_Code/commit/c2b787f3823c2b1ff0efea31a9eaf034f0b6e4bb) changed the local lifetime scope so the controller is destroyed before COM teardown. Its commit message is “fix(windows): destroy Flutter controller before COM teardown.”

The old-artifact replay ran from workflow source `90539f9f`, which already included the validator's UI Automation proxy cleanup (`2754b073`) before posting `WM_CLOSE`; the app still crashed in both themes. The later current artifact source `1129d607` contains `c2b787f` and passed the same Windows 11 ARM x64-emulation replay in [`41627307864`](https://github.com/Eternal-Wanderer-Vegetable/Alula_Code/actions/runs/41627307864): both themes edited, synchronized, saved/read back, posted `WM_CLOSE`, and exited 0 without Application Error events or dumps. This old-versus-new artifact comparison makes the application teardown fix a strong candidate mitigation and makes validator-only proxy cleanup an insufficient explanation.

This is still not a single-variable reproduction: the two binaries contain other changes, and the historical diagnostic only identifies an access violation in `flutter_windows.dll` at offset `0x1e220`, without a confirmed stack. Record the old crash as **likely mitigated by `c2b787f`; exact root cause not proven**, rather than as either a known unresolved current failure or a proven permanent fix.

The repeated current-artifact failures were separate harness input failures: keyboard/clipboard injection lost a character, the sessions exited 0, and no app fault events or dumps appeared. CI surfaced the real close crash and supported a targeted lifecycle fix, while most repeated red runs in the wider sample were probe/fixture failures rather than crashes.

This replay does not cover native ARM builds, Windows client hardware, Narrator, or manual device validation. Native macOS and Linux DRM/device gates remain separate.
