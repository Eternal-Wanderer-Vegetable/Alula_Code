# P04.113 / EDT-19c — Result-coordinate ranges for merge conflicts

Date: 2026-11-04. Status: scope registered; implementation not started. Depends on P04.112 (`e08bfe9`), which exposes the stateless three-way projection as ABI v38.

## Goal

Expose the current conflict segment's position in the projected result so a later Merge Editor can align conflict controls with Result and replace one accepted region without rebuilding or overwriting unrelated user edits. The returned range is tied to the exact projection response and must be recomputed whenever conflict resolutions change.

The reference is Code-OSS `1.145.0-dev`, commit `4bda7217fc83e8e838b1edd9ebaf21bb9b498c7e`. Its merge model maintains base/result and input/result line mappings and computes modified base ranges in [`mergeEditorModel.ts`](https://github.com/microsoft/vscode/blob/4bda7217fc83e8e838b1edd9ebaf21bb9b498c7e/src/vs/workbench/contrib/mergeEditor/browser/model/mergeEditorModel.ts), [`mapping.ts`](https://github.com/microsoft/vscode/blob/4bda7217fc83e8e838b1edd9ebaf21bb9b498c7e/src/vs/workbench/contrib/mergeEditor/browser/model/mapping.ts), and [`modifiedBaseRange.ts`](https://github.com/microsoft/vscode/blob/4bda7217fc83e8e838b1edd9ebaf21bb9b498c7e/src/vs/workbench/contrib/mergeEditor/browser/model/modifiedBaseRange.ts). The public [Merge Editor guide](https://code.visualstudio.com/docs/sourcecontrol/merge-conflicts) describes Incoming, Current, and editable Result, with Base available as an alternate view.

## In scope

- Extend `editor-merge::MergeProjection` to report each conflict's half-open result range in UTF-16 code units for the current projection. An unresolved conflict maps to its base-text fallback; a resolved conflict maps to the selected input text. A side that contributes no text may have an empty range.
- Keep the existing zero-based/end-exclusive base line range and deterministic conflict ID. Result offsets are not base offsets and are measured against the exact `result` string returned by the same projection request.
- Add `resultStartUtf16` and `resultEndUtf16` to the JSON response, bump Rust and Dart handshake together from ABI v38 to v39, and add typed fields to `AlulaMergeConflict`.
- Preserve the stateless request contract, existing size/work/conflict bounds, all-or-nothing errors, panic containment, UTF-8 validation, and output ownership through `alula_string_free`.
- Cover multiple conflicts, input insertions and deletions, empty result contributions, preceding emoji/surrogate pairs, BOM, CRLF, CR, and final-newline cases. Tests must use the real compiled library for the Dart round-trip and verify that each UTF-16 slice of the returned result equals the active conflict contribution.

## Out of scope

- Merge Editor UI, editor tabs/panes, result `AlulaDoc` creation, save/dirty/close lifecycle, navigation, commands, layout, Git conflict discovery/completion, and smart combination of both inputs.
- Changes to `DocRegistry`, existing `AlulaDoc` operations, document synchronization, IME, save protocol, or input/base line mapping semantics.
- Persistent FFI handles or session registries. Each call returns ranges valid only for that response's projection.

## Acceptance

Rust and Dart agree on ABI v39 and the exact UTF-16 result-range contract. Returned ranges are ordered, bounded by `result.codeUnits.length`, and slice the returned result to the corresponding active conflict contribution. A fresh projection after resolving an earlier conflict reports shifted ranges. The compiled-library tests cover UTF-16 and line-ending boundaries; the Rust workspace/Clippy/core build, Flutter analysis/tests, PR CI, and platform package/launch checks pass. This slice only establishes the projection contract and does not complete EDT-19 or `feat-026`.
