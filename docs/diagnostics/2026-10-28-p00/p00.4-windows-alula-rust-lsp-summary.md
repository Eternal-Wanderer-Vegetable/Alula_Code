# P00.4 Windows Rust + rust-analyzer memory samples

## Setup

The Windows Release build at `app/build/windows/x64/runner/Release/alula_app.exe` was launched from `E:\alula_code\app` with `--lsp-auto`, opening `tests/fixtures/rust-mini`. Each run used a fresh temporary `HOME` passed to the Windows process through WSLENV, so the user's existing Alula session was not used or modified. `mem-probe` sampled Windows process-tree Private Bytes once per second for 60 seconds in runs 1–3 and for 600 seconds in the idle follow-up. The fixture was opened for language-service startup; no editor input was scripted.

## Interpretation and limits

The three-run one-minute stable median is 89.84 MiB above the 500 MiB Rust + rust-analyzer target in `docs/03`. The three 10-minute idle runs had stable values 589.09/589.27/589.09 MiB (median 589.09 MiB) and final values 588.11/590.77/591.70 MiB; all remain about 89 MiB above target and show no meaningful idle growth or budget recovery. This completes three repetitions of the idle sub-scenario only. The full docs/04 memory gate still lacks 30-minute editing, VS Code comparison, other full-product services, and three-platform runs. P00.4 remains incomplete; the result does not authorize starting P01.

The three 30-minute scripted-edit runs each lasted 1800 seconds and saved 150 comments to the isolated fixture. Each mem-probe report contains 1808 one-second samples, with four processes in its last sample (Alula, two rust-analyzer processes, and the proc-macro server); the separate close check found every recorded PID exited after 30 seconds. Stable Private Bytes were 676.20/672.36/660.81 MiB (median 672.36 MiB), 160.81–176.20 MiB above the 500 MiB target. Each run repeated two watcher-path warnings and a rust-analyzer `client exited without proper shutdown sequence` warning, so process exit does not establish graceful LSP shutdown. Runs 1–2 saved through the File menu; run 3 used Ctrl+S after the test script was updated to avoid a coordinate-sensitive save click and to check foreground ownership during disk verification. Two later run-3 retries lost foreground before completion and are recorded separately; they do not count as samples. These Windows Rust+RA edit runs complete that load-duration repetition only. They do not provide VS Code comparison, other platforms, DRM WPE GBM, Microsoft service identity/licensing, or full-product service coverage; P00.4 remains blocked.

The earlier 45-second attempt with only `alula_app.exe` used the default Windows profile. Metadata-only inspection found an existing session with a workspace value that points to an existing directory. `_restoreSession` runs before the `autoFolder` branch in `_initCore`; when it restores a workspace, the `autoLsp` callback is not scheduled because `openedFolder` stays false. Repeating with a fresh temporary `HOME` opened the Rust fixture and produced the process tree above. No workspace path or document text from the existing session was included in the report.

## Same-service VS Code comparator status

The local machine has Microsoft VS Code 1.142.0 Stable and rust-analyzer extension 0.3.3089. A temporary profile and a copy of that extension were prepared to point at the same `rust-analyzer 1.97.1` executable used by Alula. Both PowerShell `Start-Process -WindowStyle Minimized` and WSH `SW_SHOWMINNOACTIVE` launches still changed the foreground window during the startup guard; each guard restored the previous foreground and stopped the isolated instance. Follow-up process checks found no matching isolated processes, and the temporary profile and extension copy were deleted. No 10-minute memory sample was captured. The safety preflight is recorded in `p00.4-vscode-rust-lsp-preflight.json`; the sampling script is `p00.4-vscode-rust-lsp-idle.ps1`. A foreground comparison requires user approval and would remain supplementary because VS Code 1.142.0 is not the pinned Code-OSS 1.145.0-dev reference.
