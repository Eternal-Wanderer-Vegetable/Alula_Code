# P04.117 / EDT-19g — Merge Editor conflict navigation and side acceptance

Date: 2026-11-05
Repository: `Eternal-Wanderer-Vegetable/Alula_Code`
Scope registration base: `42d7eb1b9ae41dfec614e66f5be92fa4ecff0dc2`

## Why this slice

P04.111–P04.116 provide the Rust projection, UTF-16 result ranges, session lifecycle, visible panes, and `_open.mergeEditor` route. The remaining EDT-19 core still lacks a way to move between unresolved conflicts and choose which frozen input supplies the active result range.

The pinned Code-OSS 1.145.0 reference is commit `4bda7217fc83e8e838b1edd9ebaf21bb9b498c7e`:

- [`commands.ts` navigation and side actions](https://github.com/microsoft/vscode/blob/4bda7217fc83e8e838b1edd9ebaf21bb9b498c7e/src/vs/workbench/contrib/mergeEditor/browser/commands/commands.ts#L352-L434) registers `merge.goToNextUnhandledConflict`, `merge.goToPreviousUnhandledConflict`, `merge.toggleActiveConflictInput1`, and `merge.toggleActiveConflictInput2` as F1 actions. Navigation wraps through unhandled ranges; side actions operate on the active range.
- [`viewModel.ts` navigation and active range](https://github.com/microsoft/vscode/blob/4bda7217fc83e8e838b1edd9ebaf21bb9b498c7e/src/vs/workbench/contrib/mergeEditor/browser/view/viewModel.ts#L116-L140) derives the active range from editor focus/caret. [`goToNextModifiedBaseRange` and `goToPreviousModifiedBaseRange`](https://github.com/microsoft/vscode/blob/4bda7217fc83e8e838b1edd9ebaf21bb9b498c7e/src/vs/workbench/contrib/mergeEditor/browser/view/viewModel.ts#L231-L309) wrap and reveal the chosen range.
- [`conflictActions.ts` per-side actions](https://github.com/microsoft/vscode/blob/4bda7217fc83e8e838b1edd9ebaf21bb9b498c7e/src/vs/workbench/contrib/mergeEditor/browser/view/conflictActions.ts#L89-L191) labels actions by input and updates the result through merge model transactions.

## Included

- Add accessible previous/next-unhandled controls and conflict status to the existing Merge Editor toolbar. Navigation uses the Rust projection's UTF-16 result ranges, wraps at either end, skips resolved conflicts, and moves the result caret to the selected conflict.
- Derive the active conflict from the result document's current UTF-16 selection. When no conflict contains the selection, side actions are disabled.
- Add accessible Input 1 and Input 2 actions for the active conflict. Register the four pinned F1 action ids above, visible only while a Merge Editor session is active and enabled only when their required conflict is available.
- Route side acceptance through `MergeResultSession.planResolveConflict` and the existing Workbench `_applyMergeResultPlan` path. Preserve Rust TextOp validation, one undoable edit, split-view synchronization, save state, and close/unresolved counts.
- If a manual result edit invalidates the projection ranges, disable navigation and acceptance until the session can safely reconcile; never jump to or edit a stale UTF-16 range.

## Acceptance evidence required

- Toolbar and F1 actions use the pinned ids/titles and remain hidden or disabled outside their context.
- Next/previous navigate in order, wrap, skip resolved conflicts, handle zero-length insertion conflicts, and place the caret using absolute UTF-16 offsets without disturbing other documents.
- Input 1/Input 2 acceptance uses the existing Rust-authoritative plan/apply path; the result, resolution map, dirty/savepoint, undo/redo, and visible unresolved count remain consistent.
- Emoji, CRLF, BOM, and conflict ranges after earlier side acceptance are covered. Stale external edits reject actions without changing text or file contents.
- Focused widget/session/Workbench tests, full local N.2 DoD, Harness, GitNexus change detection, PR CI, and Linux/Windows/macOS ARM64 platform build/launch/package results are recorded. No local GUI or Narrator is used.

## Explicit exclusions

This slice does not implement Accept Combination/smart merge, accept-all side/combination, complete-merge confirmation, Git conflict discovery, conflict-marker parsing, native decorations, or F1 resource picking. Combination and accept-all semantics require a separate EDT-19 slice. There is no Rust/ABI change, direct text mutation, change to the MergeResultSession initial-result contract, numeric memory optimization, or device-level macOS DnD/IME claim.
