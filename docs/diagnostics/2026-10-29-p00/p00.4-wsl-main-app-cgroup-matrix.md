# P00.4 WSLg 主应用 cgroup v2 限额重复扫描（2026-10-29）

## 范围与方法

以 WSLg + Xvfb + Flutter Linux Release 主应用运行。每轮均由 `systemd-run --user --scope` 建立 cgroup v2，**scope 包含 `xvfb-run`、Xvfb、应用和其子服务**；`memory.swap.max=0`。使用临时 HOME 和 `rust-mini` 副本。每轮尝试打开 `src/main.rs`、输入唯一 marker、Ctrl+S，并回读该 fixture 文件验证；每 0.5 秒采样 cgroup `memory.current` 及 cgroup 进程 `/proc/PID/smaps_rollup` PSS 合计。

基础矩阵为每模式、每档 3 次。无 RA 的 256 MiB 档第 2 次未通过目标文件 marker 校验；该次保留为失败记录，并补跑第 4 次（窗口就绪后额外等待 2 秒），重试通过。因此该档为 3/4 次成功，不能把原失败记作通过。

`no_ra` 使用 `--lsp-auto` 打开 Rust fixture，但子进程 PATH 不含 Cargo，无法启动 rust-analyzer；它是“RA 不可用”场景，不等于产品已有显式低资源策略。`ra` 使用 WSL stable rust-analyzer。环境为软件渲染，不提供真实 DRM/WPE GBM 证据。

## 结果解释

RA 启动场景中，64/128 MiB 三次均未出现窗口且 systemd scope 以 `oom-kill` 结束；256/512 MiB 三次均曾出现窗口，但 scope 在保存校验前以 `oom-kill` 结束；1 GiB 三次均保存并正常退出。无 RA 的 64/128 MiB 也均在窗口出现前 OOM；256/512/1024 MiB 的 3 次成功保存关闭已满足重复次数（256 MiB 另有 1 次失败尝试）。这些结果只描述此 WSLg/Xvfb/software-GL 主应用与 `rust-mini` 工作负载。

对极低限额，scope 在 cgroup 文件可采样前即结束，故 JSON 中的 `memory.current` 时间线可能为空；OOM 判定依据是 systemd `Result=oom-kill`，不能把缺少 `memory.events` 采样误读为无 OOM。PSS 汇总与 cgroup `memory.current` 是不同口径。

此扫描只验证短时启动/编辑/保存/关闭与限额 OOM，不替代 docs/04 每场景 1 分钟稳定、10 分钟空闲、30 分钟编辑及关闭+30 秒回收；也没有 Windows Job Object 对照。`no_ra` 不证明 Critical 降级策略已实现。

完整逐轮时间线、systemd 结果、events、PSS、hash 与命令输出见本文件同名 JSON。真实 DRM/WPE GBM、Microsoft 官方服务身份/许可、同服务 VS Code 对照及 Rust+RA 500 MiB 产品目标仍未关闭。
