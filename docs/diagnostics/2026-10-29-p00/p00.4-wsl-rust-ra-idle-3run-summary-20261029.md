# P00.4 WSLg/Xvfb Rust+RA idle observations (2026-10-29)

## Scope

Three 10-minute observations used the Flutter Linux Release app, the `rust-mini` fixture, real WSL `rust-analyzer`, a 1 GiB cgroup v2 scope, and `memory.swap.max=0`. The scope included `xvfb-run`, Xvfb, the controller, app, and language-server processes. Each valid run exited with app code 0, reported no OOM events, and had no rust-analyzer/proc-macro processes left after 30 seconds. Temporary HOME and fixture copies were removed.

Repeat 2 and 3 used focused XTest keyboard input; a separate short screenshot check confirmed `src/main.rs` was open. That screenshot check is not a memory sample. The first run predates the keyboard-input correction, so treat these as three WSLg observations rather than a perfectly controlled three-run interaction comparison.

The screenshot check ended with a close timeout and SIGTERM, so it is excluded from the table and memory evidence. Its short run is retained in `p00.4-wsl-rust-ra-idle-ui-preflight-20261029.{json,md}`; the image documents that the keyboard sequence opened the fixture file.

The two corrected repeats attribute 154.79 and 146.97 CPU seconds to `alula_app` during idle; rust-analyzer reported 0.00 CPU seconds at the 10-second process-snapshot resolution. The first run's idle CPU result was much lower. This discrepancy needs follow-up in the WSLg/Xvfb software-rendering setup; these figures do not describe native DRM/X11/Wayland desktop CPU behavior.

The measured scope PSS peaks are about 880–892 MiB. These observations do not pass the 500 MiB Rust+RA budget or complete the docs/04 product/platform pressure matrix. They do not provide native Linux DRM/WPE GBM/DMABUF evidence, a matched VS Code workload, or the outstanding Microsoft service identity/license evidence. P00.4 remains blocked/in-progress; P01 remains gated.
