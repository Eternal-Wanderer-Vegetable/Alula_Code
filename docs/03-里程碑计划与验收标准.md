# 03 · 里程碑计划与验收标准

## 0. 总览与决策门

```
Phase 0 技术验证 ──G1──▶ Phase 1 轻量编辑器(V1) ──▶ Phase 2 扩展兼容 ──G2──▶ Phase 3 生产化
   (原型A/B对照)          (无插件可用)              (VSIX/Node宿主)           (DAP/信任/回归)
                                              G2 不通过 ⇢ 备选路线：Theia 内核精简
```

| 阶段 | 主题 | 出口判据（摘要） |
|---|---|---|
| Phase 0 | 可行性验证 + 路线固定 | 对照实验数据齐备；G1 决策记录在案 |
| Phase 1 | 能独立工作的轻量编辑器 | 无 Node 宿主完成 Python/C++/Rust 补全/诊断/跳转/格式化；内存预算达标；压力测试通过 |
| Phase 2 | 目标插件兼容 | 首批 4 个 VSIX 行为级可用；G2 决策 |
| Phase 3 | 生产化 | 三平台回归绿；崩溃恢复与信任机制完备 |

**全局排序原则（讨论定稿）**：第一版不做插件商城；先做一个**在大模型占用大量资源时
仍能可靠编辑和保存代码的工作台**。LSP 已覆盖三类语言的日常开发，插件兼容是长期工程。

## 1. Phase 0：技术验证（目标：用数据固定技术路线）

### 1.1 任务分解

| # | 任务 | 产出 |
|---|---|---|
| 0-1 | 原型 B 骨架：Flutter + flutter_rust_bridge + Ropey | 「编辑→增量同步→Rust 应用→回显确认」最小闭环 |
| 0-2 | 编辑组件评测：CodeForge / Re-Editor / flutter_code_editor | 统一评测卡得分表 + 选型结论（见 1.2）。**✅ 2026-10-26 自动化部分完成**：code_forge 13 分首选 / re_editor 10 分备选 / flutter_code_editor 5 分否决（无虚拟化渲染，100 行即溢出），见 docs/06-评测-编辑组件选型.md；剩余：真机 IME 与流畅度人工复核清单（报告 §五） |
| 0-3 | 原型 B 接入 Tree-sitter + 1 个 LSP（建议 rust-analyzer） | 打开 Rust fixture：语法高亮 + 补全 + 诊断演示。**✅ 2026-10-26 完成**：editor-lsp（stdio JSON-RPC 客户端 + fake-lsp 集成测试）+ editor-lang（tree-sitter-rust 高亮 token，UTF-16 口径）+ FFI ABI v2（lsp/诊断轮询/补全/语法）+ UI 三面板；对真实 rust-analyzer 全链路实测（诊断 7 条实时推送、补全 62 项、语法 40 token，截图 docs/diagnostics/2026-10-26-lsp-demo/）。RA 协议要点已沉淀：盘符小写归一、服务端请求必须回应、推送只含语法错误（类型错误走 flycheck/didSave）、3.17 pull 方法名为 textDocument/diagnostic。遗留到 Phase 1：增量解析、诊断/补全异步化（现为轮询+阻塞 FFI）、诊断波浪线内嵌显示 |
| 0-4 | 原型 A：精简 Code-OSS（fork 后移除不需要的内置功能） | 可运行的减法版 VS Code（验证「继承架构做减法」能省多少）。**✅ 2026-10-26 完成并归因**：Code-OSS 1.144 dev 构建跑通；移除 86 个内置扩展仅省 ≈20 MiB（−1.5%，1310→1290 MiB）——内存大头是工作台本体；**G1 判定：原型 A 路线不具备竞争力，采用原型 B 自研路线**，报告见 docs/08-原型A-精简Code-OSS.md |
| 0-5 | 基准框架：`tools/mem-probe` + `tools/bench` | 三平台进程树采集脚本 + 报告模板；先测得 VS Code 基线。**✅ 2026-10-26 完成（Windows 实现与首批基线）**：mem-probe（tree/watch 模式，5 测试全绿）+ bench.py + 首批基线（alula 179.2 vs VS Code 干净实例 959.5 MiB，−81.3%，见 docs/baselines/2026-10-26/）；Linux PSS 路径已实现待 CI 验证，macOS 待做 |
| 0-6 | 对照实验：VS Code vs 原型 A vs 原型 B | 三组场景（无插件/同语言服务/同功能集）× Windows+Linux 数据。**无插件组数据齐备**：alula 179.2 / VS Code 干净 989.9 / 原型 A 全量 1310 / 原型 A 精简 1290 MiB（docs/baselines/2026-10-26/ + docs/08）；同语言服务组待 Phase 1 接入 LSP |
| 0-7 | 并行诊断：现有 VS Code 卡死归因 | `code --disable-extensions` 对照 → Extension Bisect；必要时 `code --disable-gpu`；`code --status` / Process Explorer 记录。**✅ 2026-10-26 完成并归因**：根因为系统提交内存耗尽（模型进程 python.exe 单进程提交 86–93 GB 击穿 107 GB 上限，近 30 天 5 次系统级资源耗尽事件；Code.exe 90 天 2 次 WER 崩溃，跨应用佐证）；扩展排除（+270 MiB 是代价非根因）；报告与缓解建议见 docs/07-诊断-VSCode卡死归因.md，commit 压力信号已反哺 docs/02 §6.1 |

### 1.2 编辑组件评测卡（0-2 统一口径）

每项 0–2 分，满分 16；任一 ★ 项为 0 分即一票否决：

| 项 | ★否 | 测法 |
|---|---|---|
| 1 万行文件编辑流畅度 | ★ | 打开 `tests/fixtures` 大文件，滚动+编辑，记录掉帧 |
| 中文输入法（组合/撤销/光标） | ★ | 微软拼音 + 至少一个 Linux IME |
| 多光标 | — | Re-Editor 已知缺多光标（开放 FR），验证现状 |
| 撤销/重做正确性（跨 IME 操作） | ★ | 编辑+IME 混合操作序列后逐级撤销 |
| 选区/拖放/列选行为 | — | 对照 VS Code 行为清单 |
| API 可扩展性（能否注入自定义渲染/补全源） | — | 代码走查：暴露的扩展点 |
| 大文件已知问题 | — | Re-Editor 存在 ~5 万行 SQL 卡顿 issue，实测边界 |
| 许可与维护活跃度 | — | MIT/Apache 优先；近 6 月提交 |

### 1.3 对照实验纪律（0-6，硬性要求）

- **同项目、同语言功能集**：不允许 Flutter 版关 LSP 而 VS Code 全开索引——三组场景
  （无插件 / 相同语言服务 / 相同功能集合）分别对比；
- 指标：启动峰值、稳定态、10 分钟空闲、30 分钟编辑后、关闭项目后回收情况；
- 口径：Windows 进程树 Private Bytes；Linux PSS（方法见文档 04）；
  禁止直接累加各进程 RSS；
- 环境记录：OS 版本、WebView/GPU 驱动、模型是否并行运行。

### 1.4 决策门 G1（Phase 0 → Phase 1）

满足以下全部则固定「Flutter + Rust Core + Tree-sitter + LSP + 可选 Node 宿主」路线：

1. 原型 B 空载进程树内存显著低于 VS Code 同场景（目标：差距 ≥ 3 倍）；
2. 评测卡至少一个组件总分 ≥ 12 且 ★ 项全过；否则启动「自研编辑控件」预研分支；
3. 中文输入法与 1 万行文件两项硬指标通过；
4. 原型 A 对照数据表明：做减法的 VS Code 仍显著重于原型 B（否则转入「精简 Code-OSS
   发行」备选路线并停止自研）。

**G1 输出物**：一页决策记录（数据表 + 结论 + 签署日期）归档至 `docs/decisions/`。

## 2. Phase 1：能独立工作的轻量编辑器（V1 产品）

### 2.1 任务分解

| 领域 | 任务 |
|---|---|
| 编辑基础 | 打开/保存（**原子保存 ✅ editor-doc**）、多标签（**✅**）、编码与换行符处理、查找替换、撤销重做 |
| 工作区 | 文件树（**懒加载 ✅**；文件监视待做）、项目搜索（ripgrep 流式结果）、命令面板 |
| 语法 | Tree-sitter 高亮（**token 着色预览 ✅**）/折叠/符号表；**VS Code JSON 主题 + TextMate 语法数据文件加载** |
| LSP | editor-lsp 客户端 + 注册表（**rust-analyzer ✅ 按工作区共享进程**；basedpyright+Ruff / clangd 待接）+ 按需启停 + 诊断/补全（**✅**）/跳转/悬浮/格式化 |
| Git | status/stage/commit/branch/diff/blame（CLI 封装）；提交历史简单浏览 |
| 终端 | 按需 PTY 终端面板 |
| 稳定性 | 进程监督树落地；低资源模式（Warn/Critical 两级）；崩溃恢复 journal |
| 观测 | 「帮助→进程资源面板」：进程树各成员内存/CPU 实时展示（对标 VS Code Process Explorer） |
| 打包 | 三平台 Release 构建 + 安装包（**Windows ✅**） |

**增量 1（2026-10-26）已完成上表 ✅ 部分**：多文件工作台闭环（打开文件夹→文件树→
多标签→编辑→Ctrl+S 原子保存）+ rust-analyzer 多文件接入（按工作区共享进程），
实机截图 docs/diagnostics/2026-10-26-phase1/。下一增量：撤销/重做 UI 化、查找替换、
Git 面板、文件监视、编辑器组件切换（待 0-2 人工复核）。

### 2.2 Phase 1 DoD（全部满足才进 Phase 2）

**功能**
- [ ] 无任何 VSIX/Node 宿主：Python、C/C++、Rust 三语言 fixture 上完成
      补全、诊断、跳转定义、重命名、格式化（用 `tests/fixtures` 标准工程验收）；
- [ ] VS Code 主题 VSIX（取自 Open VSX 的主题包）可直接导入生效；
- [ ] 中文输入法下编辑/撤销/光标正确；UTF-16 换算单测全绿（含 Emoji/CRLF/BOM 用例）。

**性能/内存（Release 构建，`tools/bench` 出报告）**
- [ ] 空工作台 ≤ 200 MiB（若未达，须给出归因与差距说明；≤ 300 MiB 为可接受下限）；
- [ ] 普通项目未启 LSP ≤ 250 MiB；
- [ ] Rust 项目 + rust-analyzer 稳定态 ≤ 500 MiB（服务器内存单独列示）；
- [ ] 冷启动 ≤ 2s 可交互；空闲 10 分钟 CPU ≈ 0、无内存增长；
- [ ] 同项目同功能对比 VS Code 总内存降低 ≥ 50%（主验收线）。

**稳定性（`tests/stress` 脚本化）**
- [ ] 强杀 LSP：编辑器不崩、缓冲区完好、自动重启或明确提示；
- [ ] 关闭工作区后进程树为空；
- [ ] 内存限额下（Linux cgroup / Windows Job Object 设为预算值）：
      Critical 模式生效，输入/滚动/保存仍可用；
- [ ] 断电式强杀后重启：journal 恢复未保存内容，磁盘无半写文件。

## 3. Phase 2：目标插件兼容（扩展级）

### 3.1 任务分解

1. VSIX 管理：下载/导入、包解析、版本与依赖检查、引擎声明校验、卸载清理；
2. 激活系统：激活事件最小集（`onLanguage`/`onCommand`/`workspaceContains`/`*`）；
3. Node 宿主 sidecar：进程模型、与 Rust Core 的 JSON-RPC 协议实现、崩溃隔离与重启；
4. API Bridge：`workspace`/`languages`/`window`/`commands` 四域映射；
5. 语言服务接管协议（02§3.3）：扩展激活后原生 LSP 让位；
6. 首批目标 VSIX 行为级适配：BasedPyright、Ruff、clangd、rust-analyzer（均 Open VSX）；
7. B 类（Web 扩展）评估：无 WebView 前提下需 JS 沙箱，出具成本评估再决定做否。

### 3.2 Phase 2 DoD

- [ ] 4 个目标 VSIX：安装→激活→**实际功能可用**（诊断/补全真实来自扩展）→卸载→
      资源回收，全流程在 Windows+Linux 通过；
- [ ] 扩展宿主崩溃：编辑与保存不受影响，宿主按策略重启；
- [ ] 未启用扩展时进程树仍无 Node.js（回归项进 CI）；
- [ ] 兼容性测试套件（`tests/compatibility`）沉淀为可重复执行的清单。

### 3.3 决策门 G2（自研适配层 vs Theia 内核）

若出现以下任一情况，停止扩张自研 API Bridge，评估切换 **Theia 内核精简**路线：

- 首批 4 个 VSIX 之外，每新增一个中等复杂扩展需要的工作量 ≥ 2 人周；
- 适配层开始需要复刻 VS Code 工作台内部服务（编辑器对象模型、事件语义）才能运行；
- 维护成本接近维护一个完整 IDE。

G2 同样输出一页决策记录。**这是讨论中反复强调的止损机制：不要无限扩张自研适配层。**

## 4. Phase 3：生产化

- DAP 调试支持（`editor-dap`，参考 helix-dap 组织；先 Python/pydevd 或 cppdbg 级别最小集）；
- 工作区信任机制（不信任目录默认禁用扩展激活与自动执行任务）；
- 扩展来源与完整性验证（Open VSX 签名/哈希校验）；
- 三平台回归 CI 常态化（含 IME/字体/HiDPI 专项，见文档 04§5）；
- 性能回归看板（每次发版跑基准套件，对比预算）；
- V2 缓冲区归属迁移的原型验证（Rust 权威 + 可视区缓存），据验证结果决定是否切换；
- WSL 里程碑（独立排期）：Windows 进程与 WSL Linux 进程不能当同一本地环境管理，
  由 Linux 侧代理启动语言服务器，处理 UNC/`\\wsl$\` 路径转换与工具链环境。
