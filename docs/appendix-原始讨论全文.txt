针对你的三个要求，我查了一下截至 2026 年 10 月的代码编辑器生态，发现一个比较有意思的现象：

**轻量级编辑器已经不少，但同时具备低内存占用、跨平台、直接兼容 VS Code 插件的产品仍然很少。**

问题主要不在代码编辑器本身，而在 VS Code 的插件运行机制。许多看起来很简单的插件，实际上依赖一整套 VS Code API 和 Node.js 运行环境。

所以我认为可以从两个方向选择：

- **直接使用：** 首先考虑 Eclipse Theia 或 VSCodium。如果愿意牺牲 VS Code 插件兼容性，则考虑 Zed。
- **自己开发：** 用原生技术实现轻量 GUI，把 VS Code 插件宿主作为可选的独立模块。这条路线更有研究价值，但工作量不小。

## 一、现有编辑器比较

| 编辑器 | VS Code 插件兼容性 | 低内存潜力 | Windows / Linux / macOS |
|---|---|---|---|
| <Entity category="software" value="Eclipse Theia"/> | 高，大多数插件 | 一般 | 全支持 |
| <Entity category="software" value="VSCodium"/> | 高，接近 VS Code | 一般 | 全支持 |
| <Entity category="software" value="Zed"/> | 不直接兼容 | 较好 | 全支持 |
| <Entity category="software" value="Lapce"/> | 不直接兼容 | 较好 | 全支持 |
| 自研 Rust 编辑器 | 取决于实现 | 最有优化空间 | 可以支持 |

这里的内存表现是架构层面的初步判断，不是同一硬件、同一工作负载下的实测排名。尤其在启用语言服务器和 AI 插件后，内存差异可能非常明显。

### 1. <Entity category="software" value="Eclipse Theia"/>：最值得研究的现成架构

Theia 的插件兼容性尤其值得注意。官方文档说明，它实现了 VS Code 扩展 API，并提供兼容性报告。不过部分 API 仍可能存在行为差异或仅有占位实现，因此不能认为所有插件都能完整运行。<Cite refs={["turn452433search0","turn452433search5"]}/>

**它的缺点是没有从根本上解决内存问题。** 桌面版本仍采用 Electron，后端也使用 Node.js。它的主要优势是模块化和可定制，而非天然拥有非常低的内存占用。

### 2. <Entity category="software" value="VSCodium"/>：兼容性优先

它特别适合不想重新适应编辑器、又希望尽量沿用既有 VS Code 插件的人。

但它仍然是 Electron 程序，**不会仅仅因为去除了遥测，就比 VS Code 显著节省内存**。某些微软专有扩展也存在安装或授权限制。<Cite refs={["turn488045search11","turn488045search13"]}/>

## 二、如果自己开发，我发现了一个值得重点研究的项目

<row align=start gap={3}>
  <AsyncImage query="Monaco editor VS Code syntax highlighting editor browser interface screenshot" aspectRatio="4:3" maxWidth="200px"/>
  <box flex="1" gap={2}>
    **<Link url="https://github.com/CodinGame/monaco-vscode-api" title="CodinGame/monaco-vscode-api"/>**

    这个项目试图将 VS Code 的公共 API 和各种服务集成到 Monaco 编辑器中，甚至提供 VS Code 扩展加载机制。它可能是自研路线最重要的技术基础。
  </box>
</row>

它解决了一个非常关键的问题。

微软官方的 <Entity category="software" value="Monaco Editor"/> 虽然是 VS Code 使用的编辑器核心，但微软明确说明：**Monaco 本身不能直接运行 VS Code 插件。** <Cite ref="turn787841search10"/>

而 `monaco-vscode-api` 的方案是把缺失的 VS Code 服务逐步补上，包括配置、命令、文件系统、扩展注册，以及基于 Web Worker 的扩展宿主。项目还提供了 VSIX 集成工具。<Cite refs={["turn874256search9","turn741138view2"]}/>

这意味着，我们不一定需要从头实现完整的 VS Code。

但必须注意，它不等于现成的完整 IDE，也不代表所有依赖 Node.js 的桌面插件都能直接运行。

## 三、我建议的自研架构

我更倾向于设计一个**按需加载插件宿主的轻量级编辑器**，而不是再制作一个完整的 VS Code 克隆。

这个设计的核心思想是：**编辑器可以不依赖插件宿主运行，但插件宿主不能绕过编辑器核心随意操作 UI。**

特别是两种工作模式可以共用同一套界面、文件服务和编辑缓冲区，不必开发两个独立的编辑器。

### 为什么我倾向于 Tauri + Monaco？

考虑三个因素：

| 维度 | 选择理由 |
|---|---|
| 插件兼容 | Monaco 与 VS Code 的架构更接近，可以复用 `monaco-vscode-api` |
| 内存优化 | 可以拆除不必要的服务，将插件宿主延迟加载 |
| 跨平台 | Tauri 已有 Windows、Linux、macOS 支持，不必自行处理所有窗口系统 |

但这个组合也有一个限制：Tauri 使用系统 WebView，Windows 采用 WebView2，macOS 使用 WKWebView，Linux 使用 WebKitGTK。这意味着它的安装体积可能较小，但 UI 渲染与内存使用并非各平台完全一致。<Cite ref="turn787841search12"/>

如果你追求的是绝对低内存以及严格一致的显示行为，那么可以考虑 Rust + GPUI/Floem 原生渲染。不过那会要求我们重新实现编辑器控件与大量交互，并自行将 VS Code API 映射到这些原生界面组件中，开发成本会大幅提高。

### 最大的技术困难：插件运行环境

VS Code 插件大致有两条主要运行路径。

<box gap={2}>
  <row align=start gap={2}>
    <icon name="check-circle" color="success" size="lg"/>
    <box flex="1" gap={1}>
      **Web Extensions**

      可在浏览器的 Web Worker 环境运行，适合优先通过 `monaco-vscode-api` 实现。相对容易进行隔离与按需加载。
    </box>
  </row>
  <divider color="subtle"/>
  <row align=start gap={2}>
    <icon name="cpu" color="secondary" size="lg"/>
    <box flex="1" gap={1}>
      **Node.js Extensions**

      依赖 Node.js、系统文件、子进程或其他桌面能力。需要独立的 Node.js 插件宿主，以及对应的 VS Code API、生命周期管理和通信机制。
    </box>
  </row>
</box>

这两种运行环境是 VS Code 官方扩展体系本身的区分。<Cite refs={["turn488045search1","turn488045search14"]}/>

因此，不能简单地把 `@theia/plugin-ext-vscode` 安装到 Tauri 项目中，就认为全部兼容工作已经完成。Theia 的实现还依赖其自身的后端、插件管理与 UI 服务。<Cite ref="turn452433search3"/>

真正的难点不只是让插件启动，而是让插件相信它正在一个功能完整的 VS Code 工作台里运行，并正确响应相关 API。

特别是两种工作模式可以共用同一套界面、文件服务和编辑缓冲区，不必开发两个独立的编辑器。

### 为什么我倾向于 Tauri + Monaco？

考虑三个因素：

| 维度 | 选择理由 |
|---|---|
| 插件兼容 | Monaco 与 VS Code 的架构更接近，可以复用 `monaco-vscode-api` |
| 内存优化 | 可以拆除不必要的服务，将插件宿主延迟加载 |
| 跨平台 | Tauri 已有 Windows、Linux、macOS 支持，不必自行处理所有窗口系统 |

但这个组合也有一个限制：Tauri 使用系统 WebView，Windows 采用 WebView2，macOS 使用 WKWebView，Linux 使用 WebKitGTK。这意味着它的安装体积可能较小，但 UI 渲染与内存使用并非各平台完全一致。<Cite ref="turn787841search12"/>

如果你追求的是绝对低内存以及严格一致的显示行为，那么可以考虑 Rust + GPUI/Floem 原生渲染。不过那会要求我们重新实现编辑器控件与大量交互，并自行将 VS Code API 映射到这些原生界面组件中，开发成本会大幅提高。

### 最大的技术困难：插件运行环境

VS Code 插件大致有两条主要运行路径。

<box gap={2}>
  <row align=start gap={2}>
    <icon name="check-circle" color="success" size="lg"/>
    <box flex="1" gap={1}>
      **Web Extensions**

      可在浏览器的 Web Worker 环境运行，适合优先通过 `monaco-vscode-api` 实现。相对容易进行隔离与按需加载。
    </box>
  </row>
  <divider color="subtle"/>
  <row align=start gap={2}>
    <icon name="cpu" color="secondary" size="lg"/>
    <box flex="1" gap={1}>
      **Node.js Extensions**

      依赖 Node.js、系统文件、子进程或其他桌面能力。需要独立的 Node.js 插件宿主，以及对应的 VS Code API、生命周期管理和通信机制。
    </box>
  </row>
</box>

这两种运行环境是 VS Code 官方扩展体系本身的区分。<Cite refs={["turn488045search1","turn488045search14"]}/>

因此，不能简单地把 `@theia/plugin-ext-vscode` 安装到 Tauri 项目中，就认为全部兼容工作已经完成。Theia 的实现还依赖其自身的后端、插件管理与 UI 服务。<Cite ref="turn452433search3"/>

真正的难点不只是让插件启动，而是让插件相信它正在一个功能完整的 VS Code 工作台里运行，并正确响应相关 API。

## 四、如果真要做，我建议分三个阶段

| 阶段 | 交付成果 | 验证重点 |
|---|---|---|
| 第一阶段：轻量编辑器 | Tauri + Monaco、文件树、搜索、基本 Git、LSP | 无插件情况下的内存与响应速度 |
| 第二阶段：插件兼容 | 接入 `monaco-vscode-api`，先支持主题、语法、Web 扩展，再实现 Node 扩展宿主 | 插件实际可用率，而不仅是安装成功率 |
| 第三阶段：性能工程 | 延迟加载、服务休眠、插件崩溃隔离、按需启动语言服务器 | 大型仓库、长时间运行、多语言开发 |

还有两个值得纳入设计的原则。

**第一，不要用全局单一插件宿主状态。** 应当把编辑缓冲区、Rust 核心、语言服务器和插件宿主的生命周期分开。即使插件崩溃，编辑器也必须能够继续保存文件。

**第二，不要把安装成功当作兼容成功。** 应当建立自动化测试集：安装扩展、激活扩展、调用命令、检查编辑行为、卸载扩展、释放资源，并跨三个操作系统重复验证。

内存测试也必须统计整个进程树，包括 WebView、Node.js、LSP，而不是只看编辑器主进程。可以参考这个现成的 <Link url="https://github.com/levivilet/lvce-memory-benchmark" title="编辑器内存基准测试项目"/>，其测试覆盖 VS Code、Zed、Lapce、Theia 等产品，并区分多种内存指标。<Cite ref="turn452433search13"/>

# 轻量级、跨平台、兼容 VS Code 插件的编辑器：技术方案 V1

针对你确定的使用范围，我建议采用一个更有针对性的方案：

**不开发完整的 VS Code 替代品，而是开发一个以 Rust 为核心、原生支持 LSP、同时兼容主流 VS Code 扩展的轻量编辑器。**

这与简单地给 Monaco 加一个插件加载器有所不同。我们的目标是让编辑器即使没有任何 VS Code 插件，也能正常完成绝大多数编程工作。

## 一、先明确兼容性目标

这里有一个重要发现：你需要的 Python、C/C++、Rust 等插件，其核心功能大多可以通过语言服务器协议（LSP）实现，没必要全部依赖 VS Code 扩展宿主。

但是，**实现同等功能和运行原版 VS Code 插件是两件不同的事情。**

特别是微软的扩展许可必须考虑。微软在官方 FAQ 中明确说明，其通过 Visual Studio Marketplace 发布的扩展，通常不授权在 Visual Studio 产品家族之外使用。即使部分代码开源，也不能简单认为其 Marketplace 发行包可以随意集成到自研编辑器中。<Cite ref="turn128543search1"/>

因此，我们应该优先选择开放生态中的扩展，或者直接集成开放语言服务器。

### 目标功能与实现方式

| 功能 | 优先实现 | VS Code 插件支持 |
|---|---|---|
| Python | basedpyright / Pyright + Ruff | 第二阶段支持开放扩展 |
| C/C++ | clangd | 支持 clangd 扩展 |
| Rust | rust-analyzer | 支持 rust-analyzer 扩展 |
| Git | 原生 Git CLI | 补充 Git 扩展能力 |
| 主题 | VS Code JSON 主题与 TextMate 语法 | 第一阶段实现 |
| 代码补全 | LSP Completion | 通过扩展 API 兼容其他补全提供者 |
| 调试 | DAP（Debug Adapter Protocol） | 后续支持调试扩展 |

Rust 的 `rust-analyzer` 已经在 Open VSX 发布，并具备补全、跳转、重命名、语义高亮等功能，这种开放扩展是理想的兼容目标。<Cite ref="turn258007search4"/>

这份架构将采用两种兼容形式：

- **功能级兼容：** 即使没有安装对应的 VS Code 插件，也能提供编辑、诊断、补全、格式化等能力。
- **扩展级兼容：** 对选定的原版 VS Code 扩展，能够安装 VSIX、激活扩展并调用相应 API。

前者是第一优先级，后者逐步扩大覆盖面。

Rust 的 `rust-analyzer` 已经在 Open VSX 发布，并具备补全、跳转、重命名、语义高亮等功能，这种开放扩展是理想的兼容目标。<Cite ref="turn258007search4"/>

这份架构将采用两种兼容形式：

- **功能级兼容：** 即使没有安装对应的 VS Code 插件，也能提供编辑、诊断、补全、格式化等能力。
- **扩展级兼容：** 对选定的原版 VS Code 扩展，能够安装 VSIX、激活扩展并调用相应 API。

前者是第一优先级，后者逐步扩大覆盖面。

### 1. Rust Core：负责真正的工作

Rust 核心不是单纯的 Tauri 后端，而应该被设计为一个可以独立测试的库。

它的职责是管理工作区、缓存文件元数据、处理 Git 操作、启动和停止语言服务器，并维护所有子进程的生命周期。

例如，用户打开一个 Rust 项目时，程序执行：

<box border radius="lg" padding={3} gap={2}>
  <list connector="solid" marker="number" gap={2}>
    <list-item>读取工作区与文件信息，立即显示编辑器</list-item>
    <list-item>识别 `Cargo.toml`，确定项目类型</list-item>
    <list-item>检查是否已有对应的 rust-analyzer 进程</list-item>
    <list-item>仅在需要语言功能时，启动或复用语言服务器</list-item>
    <list-item>通过 LSP 更新补全、诊断、跳转与悬浮信息</list-item>
  </list>
</box>

这里可以复用同一个工作区的语言服务器，而不是每打开一个文件就建立新进程。

Git 则直接调用本机 `git`，初期没有必要使用 libgit2 重写所有功能。项目搜索使用 `ripgrep`，终端使用 `xterm.js` 与 Rust PTY 桥接，并在用户打开终端时才启动 Shell。

### 2. Monaco：不要重复发明编辑器

Monaco 已经提供成熟的文本编辑基础，包括多光标、折叠、查找替换、撤销重做、代码提示界面等。

我们需要补充的主要是完整工作台相关服务，而不是从零写文本编辑控件。

这里继续使用：

<Link url="https://github.com/CodinGame/monaco-vscode-api" title="CodinGame/monaco-vscode-api"/>

它提供了 VS Code 风格的主题、语言、配置、文本语法和扩展服务替换模块，可以按照需要引入。<Cite refs={["turn258007search1","turn258007search3"]}/>

不过，我不建议一次性引入全部服务。每增加一个服务模块，都需要验证它带来的启动耗时、内存占用以及依赖体积。

### 3. VS Code 插件运行层：整个项目的最高风险模块

我建议将插件分为三个兼容等级：

| 等级 | 插件类型 | 实现难度 |
|---|---|---|
| A | JSON 主题、语法、代码片段等声明式扩展 | 低 |
| B | 具有 `browser` 入口的 Web 扩展 | 中 |
| C | 具有 `main` 入口、依赖 Node.js 的桌面扩展 | 高 |

VS Code 官方使用 `main` 和 `browser` 区分 Node.js 与 Web 扩展入口。只有声明式贡献的扩展甚至可以完全没有运行时入口。<Cite ref="turn561509search0"/>

**等级 C 不应该被当成 Monaco 自带的功能。**

目前 `monaco-vscode-api` 已提供 Web Worker 扩展宿主支持，但不能由此推导出完整的桌面 Node 扩展宿主已经可以直接嵌入 Tauri。我们需要另外验证 Node 宿主的运行、通信、模块解析以及扩展 API 覆盖。<Cite ref="turn128543search7"/>

我建议这部分优先研究 Theia 的现有实现。Theia 已经拥有独立插件宿主和 VS Code API 适配机制，适合参考其进程模型与服务边界。<Cite ref="turn128543search6"/>

最终插件宿主需要与 Rust Core 通过受控 IPC 通信。它不能持有编辑缓冲区的唯一副本，否则插件崩溃可能影响文件保存。

## 五、怎样才能真正降低内存？

我认为内存优化应该优先集中在**不启动无用进程、不重复提供服务、不保留无用工作区状态**，而不是一开始就追求极端的 Rust 微优化。

下面给出一组建议的工程目标。这是待验证的设计预算，不是现有原型的实测数据。

| 测试状态 | 初始设计目标 |
|---|---|
| 空白窗口、无语言服务 | 进程树私有内存尽量低于 250 MiB |
| 无项目冷启动 | 主界面 2 秒内可交互 |
| 不使用插件时 | Node 扩展宿主不运行 |
| 单一语言项目 | 不重复启动同类型语言服务器 |
| 空闲状态 | CPU 占用接近 0 |
| 关闭工作区 | 对应 LSP 和子进程可以退出 |
| 插件崩溃 | 编辑、保存与现有缓冲区不受影响 |

对于 Rust 大型工作区，rust-analyzer 自身的内存消耗可能远远超过编辑器本体。clangd 的索引缓存也类似。

因此，测试报告必须拆分编辑器本体、WebView、语言服务器和扩展宿主，并统计整个进程树。Linux 可以采用 PSS，Windows 关注 Private Bytes，macOS 关注物理内存占用指标；不能简单相加各进程 RSS，避免重复计算共享内存。

## 六、跨平台自动化测试

这部分其实有成熟的工具可以复用。

Tauri 最新的 WebDriver 文档推荐使用 WebdriverIO 与 `@wdio/tauri-service`。该方案能够测试 Windows、Linux、macOS 上的 Tauri 应用，并支持调用模拟、日志采集和真实应用测试。<Cite ref="turn216416search0"/>

我建议为编辑器建立以下测试矩阵：

| 测试类型 | 具体内容 | 通过要求 |
|---|---|---|
| 编辑可靠性 | 保存、撤销、恢复、编码和换行符 | 不丢失内容 |
| 语言服务 | Python/C++/Rust 标准测试项目 | 补全、诊断、跳转正常 |
| VSIX 兼容 | 安装、激活、实际执行功能、卸载 | 无未处理异常 |
| 性能回归 | 冷启动、长时间运行、大型仓库 | 不超过设定性能预算 |
| 故障注入 | 强制结束 LSP、扩展宿主 | 可以恢复，文件不丢失 |
| 跨平台 GUI | Windows、Linux、macOS | 输入、渲染和快捷键正常 |

尤其不能忽略中文输入法和跨平台字体问题。Tauri 采用的 WebView 在 Windows 上是 WebView2，macOS 是 WKWebView，Linux 则使用 WebKitGTK，三个平台需要分别验证输入法组合状态、光标定位、字体宽度和高 DPI 行为。<Cite ref="turn386893search5"/>

对于你经常涉及的 Windows + WSL 工作流，我建议将 WSL 工作区支持放在独立里程碑，而不是混入第一阶段。Windows 进程与 WSL Linux 进程不能被当作同一种本地环境来管理；将来需要由 Linux 侧代理启动语言服务器，避免路径转换和工具链环境混乱。

## 七、最重要的一次技术路线决策

我认为我们还应该保留一个备选方案：**使用 Theia 作为兼容性核心，再逐步精简其不需要的功能。**

两条路线有明显区别。

| | Tauri + Monaco 自研 | 基于 Theia 精简 |
|---|---|---|
| 初始内存潜力 | 更高 | 一般 |
| 插件兼容实现量 | 大 | 较小 |
| 控制核心架构 | 完全自主 | 受 Theia 架构约束 |
| 产品维护成本 | 较高 | 相对较低 |
| 最适合 | 以低内存为核心的长期项目 | 快速获得成熟插件支持 |

我的建议是：**先完成阶段 0，重点验证 Node 扩展宿主，而不要直接开始全面开发。**

如果能够在保持 Tauri 轻量架构的同时运行目标 VSIX，那么值得继续自研。反过来，如果 Node 宿主的维护成本与完整 IDE 相当，直接复用 Theia 可能更经济。

这一轮研究后，我认为最有价值的突破并不是把 VS Code 重写成 Rust，而是建立一种混合运行模式：

**普通编辑使用轻量核心，复杂语言功能调用独立服务器，只有真正需要时才启用 VS Code 扩展宿主。**

这样既能覆盖你的主要开发需求，也能避免为了兼容整个 VS Code 生态而承担过多资源开销。这个架构值得进入原型验证阶段。<MemoryCite />

这里继续使用：

<Link url="https://github.com/CodinGame/monaco-vscode-api" title="CodinGame/monaco-vscode-api"/>

它提供了 VS Code 风格的主题、语言、配置、文本语法和扩展服务替换模块，可以按照需要引入。<Cite refs={["turn258007search1","turn258007search3"]}/>

不过，我不建议一次性引入全部服务。每增加一个服务模块，都需要验证它带来的启动耗时、内存占用以及依赖体积。

### 3. VS Code 插件运行层：整个项目的最高风险模块

我建议将插件分为三个兼容等级：

| 等级 | 插件类型 | 实现难度 |
|---|---|---|
| A | JSON 主题、语法、代码片段等声明式扩展 | 低 |
| B | 具有 `browser` 入口的 Web 扩展 | 中 |
| C | 具有 `main` 入口、依赖 Node.js 的桌面扩展 | 高 |

VS Code 官方使用 `main` 和 `browser` 区分 Node.js 与 Web 扩展入口。只有声明式贡献的扩展甚至可以完全没有运行时入口。<Cite ref="turn561509search0"/>

**等级 C 不应该被当成 Monaco 自带的功能。**

目前 `monaco-vscode-api` 已提供 Web Worker 扩展宿主支持，但不能由此推导出完整的桌面 Node 扩展宿主已经可以直接嵌入 Tauri。我们需要另外验证 Node 宿主的运行、通信、模块解析以及扩展 API 覆盖。<Cite ref="turn128543search7"/>

我建议这部分优先研究 Theia 的现有实现。Theia 已经拥有独立插件宿主和 VS Code API 适配机制，适合参考其进程模型与服务边界。<Cite ref="turn128543search6"/>

最终插件宿主需要与 Rust Core 通过受控 IPC 通信。它不能持有编辑缓冲区的唯一副本，否则插件崩溃可能影响文件保存。

## 五、怎样才能真正降低内存？

我认为内存优化应该优先集中在**不启动无用进程、不重复提供服务、不保留无用工作区状态**，而不是一开始就追求极端的 Rust 微优化。

下面给出一组建议的工程目标。这是待验证的设计预算，不是现有原型的实测数据。

| 测试状态 | 初始设计目标 |
|---|---|
| 空白窗口、无语言服务 | 进程树私有内存尽量低于 250 MiB |
| 无项目冷启动 | 主界面 2 秒内可交互 |
| 不使用插件时 | Node 扩展宿主不运行 |
| 单一语言项目 | 不重复启动同类型语言服务器 |
| 空闲状态 | CPU 占用接近 0 |
| 关闭工作区 | 对应 LSP 和子进程可以退出 |
| 插件崩溃 | 编辑、保存与现有缓冲区不受影响 |

对于 Rust 大型工作区，rust-analyzer 自身的内存消耗可能远远超过编辑器本体。clangd 的索引缓存也类似。

因此，测试报告必须拆分编辑器本体、WebView、语言服务器和扩展宿主，并统计整个进程树。Linux 可以采用 PSS，Windows 关注 Private Bytes，macOS 关注物理内存占用指标；不能简单相加各进程 RSS，避免重复计算共享内存。

## 六、跨平台自动化测试

这部分其实有成熟的工具可以复用。

Tauri 最新的 WebDriver 文档推荐使用 WebdriverIO 与 `@wdio/tauri-service`。该方案能够测试 Windows、Linux、macOS 上的 Tauri 应用，并支持调用模拟、日志采集和真实应用测试。<Cite ref="turn216416search0"/>

我建议为编辑器建立以下测试矩阵：

| 测试类型 | 具体内容 | 通过要求 |
|---|---|---|
| 编辑可靠性 | 保存、撤销、恢复、编码和换行符 | 不丢失内容 |
| 语言服务 | Python/C++/Rust 标准测试项目 | 补全、诊断、跳转正常 |
| VSIX 兼容 | 安装、激活、实际执行功能、卸载 | 无未处理异常 |
| 性能回归 | 冷启动、长时间运行、大型仓库 | 不超过设定性能预算 |
| 故障注入 | 强制结束 LSP、扩展宿主 | 可以恢复，文件不丢失 |
| 跨平台 GUI | Windows、Linux、macOS | 输入、渲染和快捷键正常 |

尤其不能忽略中文输入法和跨平台字体问题。Tauri 采用的 WebView 在 Windows 上是 WebView2，macOS 是 WKWebView，Linux 则使用 WebKitGTK，三个平台需要分别验证输入法组合状态、光标定位、字体宽度和高 DPI 行为。<Cite ref="turn386893search5"/>

对于你经常涉及的 Windows + WSL 工作流，我建议将 WSL 工作区支持放在独立里程碑，而不是混入第一阶段。Windows 进程与 WSL Linux 进程不能被当作同一种本地环境来管理；将来需要由 Linux 侧代理启动语言服务器，避免路径转换和工具链环境混乱。

## 七、最重要的一次技术路线决策

我认为我们还应该保留一个备选方案：**使用 Theia 作为兼容性核心，再逐步精简其不需要的功能。**

两条路线有明显区别。

| | Tauri + Monaco 自研 | 基于 Theia 精简 |
|---|---|---|
| 初始内存潜力 | 更高 | 一般 |
| 插件兼容实现量 | 大 | 较小 |
| 控制核心架构 | 完全自主 | 受 Theia 架构约束 |
| 产品维护成本 | 较高 | 相对较低 |
| 最适合 | 以低内存为核心的长期项目 | 快速获得成熟插件支持 |

我的建议是：**先完成阶段 0，重点验证 Node 扩展宿主，而不要直接开始全面开发。**

如果能够在保持 Tauri 轻量架构的同时运行目标 VSIX，那么值得继续自研。反过来，如果 Node 宿主的维护成本与完整 IDE 相当，直接复用 Theia 可能更经济。

这一轮研究后，我认为最有价值的突破并不是把 VS Code 重写成 Rust，而是建立一种混合运行模式：

**普通编辑使用轻量核心，复杂语言功能调用独立服务器，只有真正需要时才启用 VS Code 扩展宿主。**

这样既能覆盖你的主要开发需求，也能避免为了兼容整个 VS Code 生态而承担过多资源开销。这个架构值得进入原型验证阶段。<MemoryCite />

## 一、Flutter 是否真的能解决 Tauri 的问题？

你的判断有合理依据，但需要区分两个概念：跨平台的显示一致性，以及跨平台的系统兼容性。

| 比较维度 | Tauri 2 | Flutter Desktop |
|---|---|---|
| GUI 渲染 | 系统 WebView | Flutter 自身渲染引擎 |
| Linux 图形依赖 | WebKitGTK | GTK 窗口集成 + Flutter 引擎 |
| 三平台视觉一致性 | 受 WebView 差异影响 | 通常更容易控制 |
| 无浏览器内核依赖 | 否 | 是 |
| VS Code / Monaco 复用 | 容易 | 困难 |
| 最低内存占用 | 不确定 | 不确定 |
| 自定义 IDE 工作台 | 灵活 | 灵活 |
| 代码编辑控件成熟度 | Monaco 非常成熟 | 需要额外选择组件 |

Flutter 官方已经支持 Windows、Linux 和 macOS 的原生桌面应用。它在 Linux 上依然需要 GTK 等系统依赖，但不用依赖 WebKitGTK 渲染整个应用界面。<Cite refs={["turn685463search0","turn949140search1","turn685463search14"]}/>

此外，Flutter 3.47 已经在三大桌面平台默认启用 Impeller 渲染引擎，这也有助于统一图形渲染体系。<Cite ref="turn417437search9"/>

不过，这不意味着 Flutter 完全不存在 Linux 兼容问题。例如，Linux Wayland 环境下仍有与特定 GPU 驱动、渲染器相关的内存问题报告。<Cite refs={["turn417437search8","turn417437search16"]}/>

因此，我的判断是：

- 对于**界面视觉一致性**，Flutter 更符合你的设计目标。
- 对于**减少系统 WebView 依赖**，Flutter 有明确优势。
- 对于**极低内存占用**，还不能认定 Flutter 一定胜过 Tauri，需要实际基准测试。
- 对于**VS Code 原版插件兼容性**，Flutter 反而会提高实现难度。

最后一点将是整个方案的关键。

## 二、为什么不能简单把 Monaco 放进 Flutter？

实际上，已经有人开发了 <Link url="https://pub.dev/packages/flutter_monaco" title="flutter_monaco"/> 这样的组件。

但它在桌面系统上仍然通过 WebView 运行 Monaco，Windows 使用 WebView2，macOS 使用 WKWebView。另一些 Monaco 封装还使用 Linux WebKitGTK。<Cite refs={["turn685463search9","turn685463search13"]}/>

这样虽然表面上使用 Flutter，实际上最核心的代码编辑区域仍旧依赖 WebView。

**这会抵消你更换 Tauri 的一个主要目的。**

所以，我建议放弃把 Monaco 作为主编辑控件的设计，改用纯 Flutter 编辑组件。

这意味着我们不能再直接依赖 `monaco-vscode-api` 提供工作台兼容层，但可以换来更独立、更一致的原生编辑界面。

这套结构中，我建议特别注意三个设计。

### 1. Flutter 与 Rust 通过 FFI 通信

这部分可以直接利用 <Link url="https://github.com/fzyzcjy/flutter_rust_bridge" title="flutter_rust_bridge"/>，它支持三大桌面平台、异步 Rust 函数和 Rust 与 Dart 双向调用。<Cite ref="turn417437search0"/>

但不应该每次输入一个字符，就把整个文件内容通过 FFI 传给 Rust。

更合理的方案是：

- Flutter 编辑器本地即时响应键盘输入。
- 修改内容以增量操作和版本号同步给 Rust。
- Rust 负责维护权威文档状态，并将语法与 LSP 更新返回 Flutter。
- 两侧通过版本检查防止异步结果覆盖较新的编辑内容。

另外，LSP 普遍涉及 UTF-16 位置编码，而 Rust 字符串使用 UTF-8。中文、Emoji、组合字符等场景必须处理好文本位置转换，否则会出现诊断波浪线和代码补全位置错乱的问题。

### 2. Tree-sitter 负责基础语法能力

我建议 Rust Core 使用 <Link url="https://github.com/tree-sitter/tree-sitter" title="Tree-sitter"/> 实现增量语法分析。

Tree-sitter 的设计目的之一，就是能够在文件不断修改时快速更新语法树。<Cite ref="turn692426search2"/>

它和 LSP 可以分工：

| Tree-sitter | LSP |
|---|---|
| 语法高亮 | 语义补全 |
| 代码块折叠 | 类型检查 |
| 局部结构识别 | 定义跳转 |
| 括号及结构分析 | 重命名与重构 |

对于轻量化目标，这很有意义：打开文件不一定立即启动语言服务器，也可以先提供基本的阅读和编辑体验。

### 3. VS Code 插件兼容需要重新设计

这是更换 Flutter 后，最需要认真考虑的问题。

VS Code 扩展宿主本来就支持独立的 Node.js 运行环境，并且可以根据激活事件延迟加载扩展。<Cite ref="turn692426search0"/>

我们可以借鉴这个设计：

`Flutter UI ↔ Rust Core ↔ VS Code API Bridge ↔ Node.js Host`

其中，API Bridge 将常用 VS Code API 映射到 Rust 和 Flutter 提供的能力，例如：

- `workspace`：读取文件、工作区配置、文件变更事件。
- `languages`：注册诊断、补全、代码操作提供者。
- `window`：显示信息、状态栏、输出通道。
- `commands`：注册和执行命令。

不过，**不能认为有了独立 Node.js 进程就自动兼容 VS Code 插件**。扩展还依赖大量工作台状态、编辑器对象及事件语义。

对于你的首批插件，我建议先实现等价 LSP 功能，再挑选一两个具有真实 Node.js 入口的开放 VSIX，验证原版插件激活。这会让兼容工作有明确的终点。

未来如果需要兼容使用 HTML 界面的 VS Code 插件，例如复杂的 Markdown 预览或 Webview 面板，可以允许这些特定区域使用可选 WebView，而不是让整个工作台依赖 WebView。VS Code 本身也将自定义编辑器的显示侧建立在 Webview 上。<Cite ref="turn949140search0"/>

这意味着我们必须设计两层指标：

1. **编辑器基线内存：** Flutter、Rust Core，以及打开工作区所需的基础服务。
2. **完整开发环境内存：** 基线加上真正启动的 LSP、插件、调试器和终端。

而对于你的本地模型场景，第二项决定最终体验，第一项决定架构有没有做好。

这意味着我们必须设计两层指标：

## 六、实际优化内存的五项策略

| 策略 | 具体设计 | 预期收益 |
|---|---|---|
| 延迟启动 | 只有项目需要时才启动语言服务器 | 避免空载 LSP 消耗 |
| 统一文本数据 | Rust Core 管理权威缓冲区，Flutter 负责可视区域 | 减少全文件重复缓存 |
| 虚拟化渲染 | 仅排版可见行及少量预读行 | 降低大文件显示开销 |
| 插件宿主隔离 | Node.js 不作为基础运行依赖 | 降低无插件模式的资源占用 |
| 进程生命周期管理 | 关闭工作区后回收无用索引进程 | 降低长期常驻内存 |

其中我特别想强调**文本缓冲区的所有权**。

如果使用 Re-Editor，它本身就需要维护编辑状态。Rust Core 再维护一份 Rope，就可能重复持有大量文本。

因此，第一版原型可以暂时让 Flutter 维护文本、Rust 持有用于分析的同步副本；长期则应探索由 Rust 持有权威文档、Flutter 仅缓存可见文本区域及布局结果的方案。

后一种设计更节省内存，但实现中文输入法、多光标、快速滚动和撤销同步的难度也更高。不要在原型尚未验证前，就把它认定为必然更优。

## 八、我的最终选择

经过这次调整，我会把技术优先级定为：

1. **内存开销：最高优先级。** 以真实 VS Code 开发工作流为基线，追求整体内存至少降低 50%。
2. **基础编辑体验：必须接近 VS Code。** 文件管理、Git、补全、编辑行为不能因为节省内存而严重退化。
3. **跨平台：Flutter + Rust。** 主界面不依赖系统 WebView。
4. **插件兼容：有选择地支持。** Python、C/C++、Rust 先实现 LSP 等价功能，再验证原版 VSIX。
5. **源码复用：优先复用成熟算法和开放协议。** 研究 VS Code 与 Helix，而不是从零构建每一个基础组件。

不过有一个需要明确的工程取舍：**这条路线的第一版可以实现主流插件的功能等价，却不一定能直接运行所有对应的 VS Code 扩展包。** 真正的原版插件兼容仍是独立的高风险工作项。

我现在更看好 **Flutter + Rust Core，以 VS Code 为用户体验参考，以 Helix 为 Rust 编辑模型参考** 的混合技术路线。

它不仅有机会把编辑器变得更轻，而且能让代码编辑工作台真正独立于任何特定的前端技术。将来即使 Flutter 不能满足性能目标，Rust Core 也可以保留，替换为其他 GUI，而不必重新实现整个编辑器。

**下一步最有价值的工作，就是开展 Code - OSS、Helix 和 Flutter 编辑组件的源码级可复用性审计，并建立一套能够验证“内存真的比 VS Code 少多少”的自动化基准测试。** <MemoryCite />

## 四、你的崩溃问题，其实应该改变项目的核心设计目标

你最后补充的使用场景非常重要。

**一个编辑器即使只使用 100 MiB 内存，如果系统一旦出现内存压力就无法响应键盘输入，那么它依然不是我们想要的产品。**

我建议把「低内存占用」升级成「低内存占用 + 内存压力下的稳定性」。

这里有三种需要区别对待的故障：

| 故障来源 | 可能表现 | 编辑器应该如何处理 |
|---|---|---|
| 系统 RAM 紧张、频繁换页 | 整个程序卡顿，切换窗口迟缓 | 限制缓存、避免后台内存突增 |
| GPU/驱动/图形渲染问题 | 窗口空白、界面卡死 | 保持 CPU 绘制后备路径，必要时降低渲染负担 |
| 插件或语言服务器失控 | 内存持续增长、扩展宿主崩溃 | 子进程隔离、限额、超时和自动恢复 |

这些情况不能仅凭 VS Code 总共占用了 1 GB 就区分出来。例如，VS Code 在 2026 年仍有渲染进程 V8 堆内存耗尽的相关 Issue。此类崩溃甚至可能发生在物理 RAM 尚有剩余的时候。<Cite ref="turn793701search4"/>

这一机制应当基于真实内存压力信号和可配置的预算触发，而不是简单地在内存达到某个固定百分比时强制结束所有服务。

如果 GUI 进程自己已经被操作系统阻塞甚至终止，它也不能保证恢复。因此还需要独立的文档恢复日志、定期检查点，以及文件原子保存机制。

在 Linux 上，可以结合 cgroup v2 与 PSI 做压力测试；Windows 则需要使用对应的内存和进程资源监测机制。两边的实现不同，但测试目标应该一致。

## 五、在真正开发之前，还可以先排查一下 VS Code

鉴于你说 VS Code 在运行模型时特别容易卡死，我建议先做一次不会干扰模型计算的对照诊断。

在 Windows 终端中执行：

```powershell
code --disable-extensions
```

然后在相同模型工作负载下，观察 VS Code 是否仍然出现卡死。如果问题消失，可以用 VS Code 自带的 `Help: Start Extension Bisect` 定位具体扩展；如果问题仍然存在，则应继续检查工作台进程、文件监视、内存压力与图形渲染。

微软官方推荐使用 `Help → Open Process Explorer` 或 `code --status` 查看进程情况。<Cite ref="turn881481search1"/>

另外，如果问题表现为窗口空白、渲染异常，也可以单独试验：

```powershell
code --disable-gpu
```

这是 VS Code 官方提供的图形问题排查方式，但它会改为软件渲染，可能增加 CPU 开销，因此不建议在未经验证时永久启用。<Cite ref="turn881481search4"/>

## 四、你的崩溃问题，其实应该改变项目的核心设计目标

你最后补充的使用场景非常重要。

**一个编辑器即使只使用 100 MiB 内存，如果系统一旦出现内存压力就无法响应键盘输入，那么它依然不是我们想要的产品。**

我建议把「低内存占用」升级成「低内存占用 + 内存压力下的稳定性」。

这里有三种需要区别对待的故障：

| 故障来源 | 可能表现 | 编辑器应该如何处理 |
|---|---|---|
| 系统 RAM 紧张、频繁换页 | 整个程序卡顿，切换窗口迟缓 | 限制缓存、避免后台内存突增 |
| GPU/驱动/图形渲染问题 | 窗口空白、界面卡死 | 保持 CPU 绘制后备路径，必要时降低渲染负担 |
| 插件或语言服务器失控 | 内存持续增长、扩展宿主崩溃 | 子进程隔离、限额、超时和自动恢复 |

这些情况不能仅凭 VS Code 总共占用了 1 GB 就区分出来。例如，VS Code 在 2026 年仍有渲染进程 V8 堆内存耗尽的相关 Issue。此类崩溃甚至可能发生在物理 RAM 尚有剩余的时候。<Cite ref="turn793701search4"/>

### 对新编辑器，我会增加一个独立的「低资源模式」

  </row>
  <text color="secondary" size="sm">在资源紧张时，优先保证文本编辑、保存和界面交互，而不是坚持完整的 IDE 后台功能。</text>

这一机制应当基于真实内存压力信号和可配置的预算触发，而不是简单地在内存达到某个固定百分比时强制结束所有服务。

如果 GUI 进程自己已经被操作系统阻塞甚至终止，它也不能保证恢复。因此还需要独立的文档恢复日志、定期检查点，以及文件原子保存机制。

在 Linux 上，可以结合 cgroup v2 与 PSI 做压力测试；Windows 则需要使用对应的内存和进程资源监测机制。两边的实现不同，但测试目标应该一致。

## 五、在真正开发之前，还可以先排查一下 VS Code

鉴于你说 VS Code 在运行模型时特别容易卡死，我建议先做一次不会干扰模型计算的对照诊断。

在 Windows 终端中执行：

```powershell
code --disable-extensions
```

然后在相同模型工作负载下，观察 VS Code 是否仍然出现卡死。如果问题消失，可以用 VS Code 自带的 `Help: Start Extension Bisect` 定位具体扩展；如果问题仍然存在，则应继续检查工作台进程、文件监视、内存压力与图形渲染。

微软官方推荐使用 `Help → Open Process Explorer` 或 `code --status` 查看进程情况。<Cite ref="turn881481search1"/>

另外，如果问题表现为窗口空白、渲染异常，也可以单独试验：

```powershell
code --disable-gpu
```

这是 VS Code 官方提供的图形问题排查方式，但它会改为软件渲染，可能增加 CPU 开销，因此不建议在未经验证时永久启用。<Cite ref="turn881481search4"/>

我还会提出一个关键的开发顺序调整：

**第一版不做插件商城，先做一个能够在大模型占用大量资源时，仍然可靠编辑和保存代码的工作台。**

因为 LSP 已经能满足 Python、C/C++、Rust 的绝大多数日常开发能力，而真正兼容 VS Code 插件是一个可以逐步完善的长期工程。

如果第一版就能在与 VS Code 相同的项目和模型负载下，显著降低内存占用，并表现出更少的卡顿和崩溃，那么即使插件兼容程度暂时不高，它也已经解决了你最初的问题。

我认为值得把 CodeForge、Lapce、DSCode 和 LVCE Benchmark 确定为这个新项目的**首批四个重点技术参考**。它们分别对应编辑控件、Rust 内核、扩展兼容和内存压力验证，能够大幅减少从零探索的工作量。
