# 07 · 诊断：VS Code 卡死/崩溃归因（Phase 0 任务 0-7）

> 诊断日期：2026-10-26 · 机器：Windows 11 25H2 · 61.4 GB RAM · 提交上限 107.4 GB
> 方法：事件日志取证（WER/Resource-Exhaustion/驱动错误）+ 扩展清单盘点 + A/B 对照实验
> 工具：`tools/diag-vscode.ps1`、`tools/diag-exhaustion.ps1`、`tools/diag-ab.ps1`（保留可复跑）

## 结论（证据链完整）

**卡死/崩溃的根因是系统提交内存（commit）耗尽，元凶是模型推理进程（python.exe，
单进程提交 86–93 GB）；VS Code 是受害者而非原因，扩展亦无关。**

证据链：

| # | 证据 | 来源 |
|---|---|---|
| 1 | 近 30 天 **5 次系统级虚拟内存耗尽事件**（10-16、10-17、10-18、10-20×2），事件明确记录：`python.exe 使用了 92628393984 字节`（≈86 GiB）、vmmemWSL 2.5–6.7 GB、ChatGPT.exe 2.5–4.2 GB | System 日志，Resource-Exhaustion-Detector |
| 2 | 提交上限 107.4 GB（RAM 61.4 + 页面文件可扩展 ~46 GB，自动管理、位于 C: 且 C: 仅剩 37 GB）——模型进程一家就占掉 86–93 GB，余量被击穿 | Win32_OperatingSystem / Win32_PageFileSetting |
| 3 | Code.exe 近 90 天 **2 次 WER 崩溃报告**（10-08 v1.140、08-24 v1.134）；同期 **OpenCode.exe、ZCode.exe 也各崩溃一次**——跨应用崩溃指向环境因素而非单一应用 | Application 日志 WER 1001 |
| 4 | A/B 实测（rust-mini，45s 采样）：带 25 个扩展稳态 **1257.5 MiB**（峰值 2051.7），无扩展稳态 **989.9 MiB**——扩展叠加大约 +270 MiB，是压力窗口里的「雪上加霜」，不是根因 | `tools/diag-ab.ps1`（隔离实例，不影响用户会话） |
| 5 | GPU：90 天仅 1 次 nvlddmkm 错误（09-26，Level 2）——非主要因素 | System 日志 |

一句话：**你观察到的「跑模型 → VS Code 卡死」是系统提交内存被模型进程打满后的
全局性分配失败/停顿，VS Code（Electron 多进程 + V8 大量内存预留）只是最显眼的受害者。**

## 给你的即时缓解建议（按性价比排序）

1. **给模型运行时设内存上限**：按所用推理框架限制 RAM/提交（如 torch 系的内存分配配置、
   llama.cpp 系的 `--no-mmap`/mlock 取舍、或直接用 Job Object 包一层上限）。
   让 python.exe 的提交峰值从 90 GB 降到预算内，是唯一治本项。
2. **在 E: 盘加页面文件**（E: 有 1.4 TB 空闲）：如初始 32 GB / 最大 128 GB。
   当前页面文件在 C:（仅剩 37 GB）且自动管理，扩展空间受限；提高提交上限可避免击穿。
3. **限制 WSL 内存**：`.wslconfig` 中 `memory=16GB`（实测 vmmemWSL 波动 2.5–6.7 GB，偶发更高）。
4. 模型会话期间留意提交余量（任务管理器「已提交」两段数字），余量 <10% 时就是卡死前兆。

## 对本项目的反哺（已落入设计）

1. **低资源模式的压力信号必须包含提交内存百分比**，不能只看物理内存——本机的
   故障模式是 commit 耗尽（物理内存可能尚有余量）。已更新 docs/02 §6.1。
2. 编辑器在 commit 耗尽下的行为需求得到实证：分配失败时的「必须保留」清单
   （输入/滚动/撤销/保存）与 journal 设计（docs/02 §6.3）正是应对本机场景的。
3. 扩展栈的内存代价实测：25 个扩展 +270 MiB 稳态 / +575 MiB 峰值——
   Phase 2 扩展宿主的按需启动设计（docs/02 §7）有了量化依据。
