# 01 · 目标与总体架构

## 1. 项目定位

> 在保留 VS Code 主流开发体验（Python / C++ / Rust / Git / 主题 / 补全）的前提下，
> 尽可能降低编辑器自身的常驻内存开销，并让语言服务器、插件等额外服务**按需运行**；
> 在系统内存紧张（如本地大模型并行运行）时，仍能可靠地编辑与保存代码。

成功的判据不是「比别的编辑器启动快」，而是：**在用户真实的高内存压力工作环境中，
比 VS Code 少占用 ≥50% 内存，且更少卡顿与崩溃。**

## 2. 目标分解

### 2.1 两层内存指标（所有讨论与验收都基于此区分）

| 指标 | 定义 | 为什么重要 |
|---|---|---|
| **编辑器基线内存** | Flutter 进程 + Rust Core + 打开工作区的基础服务（无 LSP、无扩展宿主） | 检验架构本身是否轻量 |
| **完整开发环境内存** | 基线 + 实际启动的 LSP / 扩展宿主 / 调试器 / 终端 | 决定用户（跑模型的机器）的最终体验 |

关键认知：如果继续运行同一个吃 400 MiB 的语言服务器，换 GUI 省不掉这 400 MiB。
因此优化重心是「不启动无用进程、不重复提供服务、不保留无用状态」，
而不是一开始就做极端的微优化。语言服务器自身内存必须单独归因、单独汇报。

### 2.2 稳定性目标（与内存同级的验收维度）

内存压力下的三类故障必须分别设计对策：

| 故障来源 | 表现 | 设计对策 |
|---|---|---|
| 系统 RAM 紧张、频繁换页 | 整机卡顿、窗口切换迟缓 | 低资源模式（见 02§6）：限制缓存、暂停后台索引、避免内存突增 |
| GPU/驱动/渲染问题 | 窗口空白、界面卡死 | Flutter 软件渲染后备路径；VS Code 同类问题的教训是 V8 堆耗尽可能发生在物理内存尚有余量时 |
| 子进程失控（LSP/扩展） | 内存持续增长、扩展宿主崩溃 | 进程隔离 + 限额 + 超时 + 自动重启；**绝不能持有编辑缓冲区的唯一副本** |

### 2.3 功能目标

- 无任何 VS Code 扩展时，即可完成：编辑/保存、文件树、项目搜索、命令面板、
  基础 Git（提交、分支、暂存、Diff、Blame）、按需终端；
  Python/C/C++/Rust 的**补全、诊断、跳转、格式化**（通过直连语言服务器）。
- 主题与语法：直接兼容 VS Code JSON 主题与 TextMate 语法体系（数据文件级兼容，不跑插件）。
- 扩展级兼容（Phase 2 起）：安装/激活来自 Open VSX 的 VSIX，首批目标
  BasedPyright、Ruff、clangd、rust-analyzer。

## 3. 总体架构（定稿）

```
┌───────────────────────────────────────────────────────────┐
│                    Flutter Workbench                        │
│  窗口 · 文件树 · 编辑视图(候选组件) · 标签页 · 命令面板      │
│  Git 面板 · 终端 UI(xterm 交互层) · 设置 · 状态栏           │
│  原则：只做显示与交互，不承担后台索引与语言分析              │
└────────────────────────┬──────────────────────────────────┘
                         │ flutter_rust_bridge (FFI)
                         │ · 增量文本操作（带版本号）
                         │ · 状态/事件流（诊断、语法、LSP 结果）
                         │ · 可视范围请求（虚拟化渲染）
┌────────────────────────┴──────────────────────────────────┐
│                    Rust Editor Core                         │
│  （workspace 库，独立于 Flutter，可单元测试/性能测试）       │
│                                                            │
│  editor-buffer   文本 Rope(Ropey) · 行索引 · 增量事务       │
│  editor-lang     Tree-sitter 增量语法 · 语法/折叠/符号      │
│  editor-lsp      LSP 客户端 · 服务器生命周期/复用           │
│  editor-workspace 文件监视 · 项目搜索(ripgrep) · Git 服务   │
│  editor-process  子进程监督树 · 限额 · 重启策略             │
│  editor-rcm      低资源模式 · 内存压力信号 · 降级控制       │
│  editor-doc      原子保存 · 恢复日志 · 检查点               │
└──────┬──────────────────────────────────┬─────────────────┘
       │ spawn/supervise                   │ 受控 IPC( stdin/stdout JSON-RPC )
┌──────┴─────────────┐        ┌───────────┴─────────────────┐
│ 语言服务进程（按需） │        │ 可选 Node.js 扩展宿主        │
│ rust-analyzer      │        │ · 默认不存在该进程            │
│ clangd             │        │ · VS Code API Bridge 适配层  │
│ basedpyright/Ruff  │        │ · 崩溃隔离，不持有缓冲区      │
└────────────────────┘        └─────────────────────────────┘
```

### 模块职责表

| 模块 | 职责 | 明确不做的事 |
|---|---|---|
| Flutter Workbench | 渲染、输入法、交互、面板 UI | 不做语言分析、不做索引、不管理子进程 |
| editor-buffer | 权威/镜像文本状态、增量事务、UTF-16↔UTF-8 换算 | 不做 UI 概念 |
| editor-lang | Tree-sitter 语法树（高亮/折叠/结构） | 不做类型级分析（归 LSP） |
| editor-lsp | LSP 客户端、服务器注册表、按需启动、一区一服务器复用 | 不实现语言服务器本体 |
| editor-workspace | 文件监视、ripgrep 搜索、Git（调用本机 `git`，V1 不用 libgit2） | 不做远程工作区（WSL 里程碑再议） |
| editor-process | 所有子进程的监督树、资源限额、崩溃重启 | 不与业务逻辑耦合 |
| 扩展宿主（可选） | VSIX 加载、激活事件、vscode.* API 适配 | 不持有缓冲区唯一副本；不直接操作 UI |

### Tree-sitter 与 LSP 的分工

| Tree-sitter（零进程成本） | LSP（按需进程成本） |
|---|---|
| 语法高亮 | 语义补全 |
| 代码折叠 | 类型检查/诊断 |
| 局部结构识别（括号、符号） | 定义跳转 |
| 缩进/结构辅助 | 重命名与重构 |

打开文件 ≠ 启动语言服务器：先给基本阅读/编辑体验（Tree-sitter），
语言功能首次被需要（补全触发、保存诊断等）才拉起 LSP。

## 4. 关键架构决策记录（ADR 摘要）

| # | 决策 | 理由 | 放弃的备选 |
|---|---|---|---|
| D1 | 前端用 **Flutter Desktop**，不用 Tauri | Tauri 依赖系统 WebView（Linux 上 WebKitGTK 支持差、三平台渲染不一致）；Flutter 自绘引擎（Impeller）跨平台一致 | Tauri 2 + Monaco |
| D2 | **不引入 WebView 跑 Monaco**；编辑控件用 Flutter 原生组件 | flutter_monaco 等封装仍靠 WebView2/WKWebView/WebKitGTK 渲染核心编辑区，抵消 D1 的目的 | Monaco + monaco-vscode-api（其 Web Worker 扩展宿主方案随 D1/D2 一并退役，仅保留思想参考） |
| D3 | **Rust Core 独立成库**，Flutter 仅是可替换的显示层 | 核心可单独测试；将来 Flutter 不达标可换 GUI 而不重写编辑器 | Rust 逻辑写进 Flutter 插件 |
| D4 | **功能级兼容优先**：Python/C++/Rust 先直连语言服务器（basedpyright/Ruff、clangd、rust-analyzer） | 这三条语言的核心 IDE 能力本质上就是 LSP 能力；装不装原版扩展对日常开发影响小 | 第一版就做 VSIX 兼容 |
| D5 | **扩展宿主是可选独立进程**，默认不启动 | 无插件模式进程树中不存在 Node.js；插件崩溃不影响编辑/保存 | 内嵌 JS 运行时 |
| D6 | **V1 缓冲区归属：Flutter 侧持有编辑态，Rust 持同步分析副本** | 降低 V1 复杂度（IME、多光标、撤销同步难度高）；V2 再评估「Rust 权威 + 可视区缓存」 | V1 直接做 Rust 权威缓冲区（风险过高） |
| D7 | **Git 调用本机 CLI**，V1 不引入 libgit2 | 覆盖 90% 需求（status/add/commit/branch/diff/blame），实现成本最低 | libgit2/git2-rs 绑定 |
| D8 | **扩展只从 Open VSX / 合法 VSIX 获取** | 微软 Marketplace 发行包按其条款不授权 VS 家族之外的产品使用 | 拉取微软 Marketplace |

## 5. 为什么这条路线值得做（讨论结论存档）

- 现有项目各自解决了局部问题，但没有组合成目标产品：
  Zed/Lapce = 原生工作台但**不兼容 VS Code 扩展**；VSCodium/Theia = 兼容但**仍是 Electron**；
  没有项目同时满足「原生工作台 + Rust 核心 + 主流 VSIX + 显著低内存」。
- VS Code 分层（code/workbench/editor/platform·base）中，可复用的是**算法与设计**
  （Piece Tree 缓冲区、编辑行为、命令/快捷键体系、TextMate 主题体系），
  而非直接搬代码——其核心是 TypeScript 且依赖 DOM；为复用而嵌入 JS 运行时违背内存目标。
- Rust 侧优先复用成熟构件：**Ropey**（rope 文本结构）、**Tree-sitter**（增量语法）、
  参考Helix 的 `helix-core`/`helix-lsp`/`helix-dap` 模块划分（注意 MPL-2.0 文件级要求，
  参考、引用、重写均可，直接复制需遵守条款）。
- 工程取舍（明确告知预期）：**第一版实现主流插件的功能等价，但不保证直接运行所有
  对应 VSIX**；原版插件兼容是独立的长期高风险工作项。
